## The deliverable — ONE design doc: `docs/design/2026-07-05-provable-privacy-record-design.md`
The flagship: **the Provable Privacy Record** — per client, per AI interaction: what left this machine (destination, mode, model — already have) PLUS **what the AI read** (the retrieved sources behind each answer), retained as a tamper-evident, exportable record a compliance officer can verify. The sentence to design for: *"Show me exactly what produced this answer, and prove my client's data never left"* — answered with evidence, not assertion.

Design must cover, concretely:
1. **The record schema** — what's captured per interaction (source file IDs/names + content hashes? snippet hashes vs full snippets — privacy/size trade-offs argued), where it lives (extend the SQLCipher audit store? per-client files? — argue it against the layer DAG and the E2EE-relay rule), and how it binds to the existing audit chain's tamper-evidence (reuse the seal/high-water-mark machinery — do NOT invent a second integrity mechanism).
2. **Retention interplay (E5 + R10 folded in):** rethink "Summary only" (today it deletes the accurate transcript and keeps the AI's interpretation — an examiner's inversion). Propose the retention matrix (what firm tier defaults to, what carries compliance warnings, whether Summary-only survives at all) and the citation-integrity rule (a note whose cited audio/transcript is deleted gets annotated, never silently dangles — the record retains the hashes so "it existed and matched" remains provable even after deletion).
3. **The export artifact** — what the CCO actually receives (per-client bundle: interactions, sources-read, destinations, consent/notice trail, integrity proof + a verification method a non-engineer can run), and how it composes with the existing Confidentiality Report + Data Map rather than being a fourth overlapping surface.
4. **R2 folded in:** move consent/jurisdiction setup to client creation (state on file, standing preferences), so record-time becomes a light confirmation — spec the client-creation addition + the record-time reduction.
5. **Honest boundaries:** what this record deliberately does NOT prove (it can't prove the provider deleted its copy; it proves what was sent and read, not what the model did) — the design must say so, in the product's honest voice, so the feature never overclaims (that's how we got here).
6. **Build plan:** rungs (like the Notice Card ladder), each shippable; effort class per rung; which rungs are Rust vs TS; test strategy per rung; migration for existing workspaces.

Constraints: fully local (the record must never itself become an egress path); never rename locked identifiers; performance (recording sources per answer must not slow Ask perceptibly — argue the write path); the privacy of the record itself (it concentrates sensitive metadata — it must live inside the same protections as the data it describes).
