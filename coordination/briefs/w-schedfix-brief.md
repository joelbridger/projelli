**The bug (verified against the code):** `run(task)` does `owned.add(id)` → `store().begin(...)` → `attempt(task, 0)`, but does NOT cancel any prior in-flight `attempt`/retry-timer for the SAME `task.id`. So if the same source/mail-folder scope changes again before its previous retag settles, the OLD timer chain stays alive with the OLD privilege/client captured in its closure. A stale retry can then (a) apply the OLD scope value, or (b) call `store().remove(task.id)`/`markFailed(task.id)` on an id that now represents the NEWER intent — clearing the newer entry or dropping the old-matter exclusion while rows are still tagged old. That reopens the exact wrong-client exposure QA-44 closes.
**Fix (do it right, robustly):** make `run(task)` supersede any existing work for the same `task.id` — cancel/clear the prior attempt's pending retry timer AND version attempts so a stale (superseded) attempt can neither apply its scope value nor mutate the store entry for that id. Track per-id: the active timer(s) and a monotonically increasing generation/epoch; on `run()`, bump the epoch and cancel prior timers; inside `attempt`, no-op (do not apply value, do not remove/markFailed) if its captured epoch != the current epoch for that id. Keep `disposeAll()` semantics intact.
