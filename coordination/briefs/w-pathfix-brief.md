# Worker brief — Windows verbatim-path bug in pathguard's absolute walk (capture_start blocker class)

**Lane:** cc-lantern-pathfix · worktree `~/lp-pathfix` · branch `lp/pathguard-windows-verbatim`
**Model:** Opus 4.8 · high (security-adjacent correctness; Windows path semantics are subtle).
**CARGO_TARGET_DIR:** `$HOME/.cargo-target-lp-pathfix` (seeded warm). `timeout 1200` on all cargo.

## The observation (once, on the Azure cloud bench — not yet a controlled repro)
Invoking `capture_start` over CDP returned: `cannot canonicalize : The system cannot find the path specified. (os error 3)` — note the EMPTY path in the message. Full context: `coordination/azure-bench/VIRTUAL-AUDIO-SPIKE.md` §Known-issue 2. Hypothesis (from the flagger, plausible per my own read): `pathguard::canonicalize_symlink_safe_absolute` walks components with `existing = PathBuf::new()` and `existing.join(component)`; on a Windows verbatim path (`\\?\C:\...`, which `Path::canonicalize()` ALWAYS returns on Windows, and `guard_matter_folder` joins input onto a canonicalized root) the `Prefix`/`RootDir` components likely fail `symlink_metadata` (`\\?\C:` alone is not statable), flipping `still_existing=false` immediately → everything lands in `tail` → final `existing.canonicalize()` runs on an EMPTY path → exactly the observed error.

Write failing tests FIRST: a `#[cfg(windows)]` test with a real verbatim path, AND (so our Linux gate also guards the logic) platform-neutral tests of the component-walk behavior for paths whose first components aren't `Normal` (on Unix an absolute path's `RootDir` component hits the same walk — check whether `existing.join("/")` even accumulates correctly; `PathBuf::join` with a rooted component REPLACES the base, another latent hazard in this function).
