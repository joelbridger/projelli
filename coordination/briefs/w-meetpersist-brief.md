## The bug (found live on the Legion — evidence: docs/evidence/meetings-verify-20260704/RUN-LOG.md on lp/windows-smoke-evidence)
Record a meeting (real one recorded today: consent → ~3.5min two-party Teams call → stop → meeting appears). Close the app, reopen: the client's Meetings tab shows "No meetings yet" — the new meeting AND older recordings all gone from the list. Direct filesystem check: every meeting folder + audio file is intact on disk. So the on-disk truth is fine; the app fails to re-DISCOVER meetings on a fresh launch. Suspects to investigate (verify, don't assume): meetings store hydration only reflecting in-session state (persisted store state vs a real folder scan), a scan that never runs on launch, matter/client scoping filter mismatching on rehydrated state, or Windows path-shape sensitivity in the scan (this repo has history there — see lp/pathguard-windows-verbatim). Note the meetings shown BEFORE restart included ones created in-session; after restart NOTHING shows, including pre-existing ones — which smells like the list is fed only by in-memory/in-session state, never a disk scan.

## What to build
On launch (and on Meetings-tab open), the app must rebuild the meetings list from the on-disk truth for each client — robustly (missing/partial folders tolerated; meeting.json the source of record; orphaned/incomplete entries surfaced honestly in the needs-review queue rather than hidden). Unit/integration tests: restart-simulation (fresh store + existing disk state → list populated correctly + client-scoped). Cover the Windows path shape in tests if the scan is path-sensitive.
