## BUG-001 — Stale global provider indicator  ·  Severity: Minor  ·  ⚪ needs-desktop-confirm → 🟡
**Found:** browser clean-slate sweep. After adding *only* an OpenAI key (real wizard), the top "All matters" trust banner still reads **"Sent to your Anthropic account"**, while the Search surface correctly shows "Sent to your OpenAI account". The global banner is out of sync with the resolved provider.
**Impact:** misleading trust/privacy signal (which provider sees your data) — sensitive for this product.
**Fix plan:** Find the top-banner confidentiality/trust component (renders "Sent to your X account") and the provider-resolution it reads. It appears to read a hardcoded/global default = Anthropic rather than the *resolved active provider* (or the provider the user actually has a key for). Make the global indicator derive from the same resolution the Search/matter uses, falling back to "the configured key" when there's no Anthropic key. Add a unit test asserting the banner reflects the configured provider when only a non-Anthropic key exists.
**Confirm:** reproduce on the desktop (where the real keychain/provider path runs) before/with the fix.

## BUG-008 — Email sync spins on "Syncing…" forever with no timeout/error/reconnect  ·  Severity: Important (UX)  ·  🟡 fix planned
**Found + CONFIRMED on real Windows (2026-06-20)** while live-confirming BUG-007. Opening the Email tab correctly auto-triggers a sync (BUG-007 fix working) — the button shows "Syncing…". But it then **stays "Syncing…" for 2.5+ minutes with 0 emails imported, no error message, no timeout, and no "reconnect" prompt.** No alert/toast anywhere. The "Sync now" button is disabled the whole time, so the user can't even retry.
**Likely root of the *empty* result:** the connected Microsoft 365 account's OAuth token is stale/expired (the original sign-in was a while ago), so the sync authenticates-or-fetches nothing. Proving full mail import end-to-end needs Jameson to reconnect Outlook (a one-time 🖐️ login) — that's a separate confirmation, not this bug.
**The bug itself (independent of the token):** a sync that can't complete must not leave the user on an infinite silent spinner. **Impact:** any user with an expired token (a normal occurrence) sees a permanently "broken" Email tab with no recourse.
**Root cause CONFIRMED in code (2026-06-20):** `src/features/settings/MailConnect.tsx` `connect()` does `mailSyncAll(...).catch(...)` — the `.catch` only fires on a *thrown* error. A sync that **hangs** (stale token: the fetch neither completes nor throws) leaves `progress.status` on `'syncing'` forever, so the spinner never resolves. **And there is NO disconnect / reconnect / sign-out control anywhere for a connected Microsoft 365 account** (grep of `MailConnect.tsx` + `account/` = zero hits; the connected state renders only "Connected." + sync progress). So a user (or Claude) with a stale Microsoft connection has **no way in the app to re-authenticate** — it's a permanent dead-end. This is the concrete blocker that stopped the live Outlook-reconnect during testing.
**Fix plan:** (a) put a timeout on `mail_sync_all` (or detect an auth failure) so the sync resolves; (b) on failure/timeout, replace "Syncing…" with a clear error state ("Couldn't sync — your Microsoft 365 sign-in may have expired"); (c) **add a "Reconnect" + "Disconnect" control to the Microsoft 365 (and Gmail) connected state** so a stale account can be re-authenticated or removed — this is required to ever refresh an expired sign-in; (d) re-enable "Sync now" once the attempt ends so the user can retry; (e) a Rust/unit test on the timeout + error-surfacing path and a UI test that the reconnect control appears when connected. (Relates to the v3.3.5 fault-isolation work; this is the *no-feedback-on-stuck-sync* + *no-way-to-reconnect* gap.)
**Confirm:** after Jameson reconnects Outlook, re-drive: sync should complete with real mail (also validates the v3.3.x Deleted-Items/Junk-exclusion + per-provider progress).

## BUG-009 — AI redline ("Revise with AI" on a .docx) is dead for any non-Anthropic BYOK provider  ·  Severity: Important  ·  🟢 fixed (uncommitted, live-verifying)
**Found + CONFIRMED on real Windows (2026-06-20)** while driving E4 (the flagship Word AI-redline). On the test bench only a valid **OpenAI** key is configured (the trust bar correctly reads "Sent to your OpenAI account"). Opening a .docx → "Revise with AI" shows the composer with an amber **"Add an account key for your AI provider … to use AI redline"** warning and the **"Suggest changes" button disabled** — even though OpenAI is configured and works everywhere else (Search/Ask, trust bar, key "Check" = Working).
**Impact:** AI redline — a headline 3.0 feature — is **completely unusable** for every BYOK user whose provider isn't Anthropic (OpenAI, Google), despite a valid key. Looks broken for most real users.
**Root cause (confirmed in code):** `src/app/shell/layout/MainPanel.tsx` renders `<DocxEditor>` and only passed `aiProvider` in Local-only mode (`'ollama'`); otherwise it passed nothing, so `DocxEditor` used its default prop `aiProvider = 'anthropic'`. `DocxEditor` then computes `redlineKey = apiKeys.find(k => k.provider === aiProvider && k.isValid)` → no Anthropic key → `redlineReady = false` → disabled. Same default-provider-mismatch family as BUG-001/004, but in the redline surface.
**Fix (applied, uncommitted):** `MainPanel` now resolves the active provider with the existing `useActiveEgressProvider(confidentialityMode)` hook — the single source of truth the trust bar + Privacy Center use (the BUG-001 fix) — and passes it as `aiProvider` to `DocxEditor` always. The hook returns `'ollama'` in Local-only (preserving prior behaviour) and the resolved cloud provider otherwise. `createProvider` already defaults the model per provider, so no model needs threading. 4 unit tests on the composer key-gate added (`tests/unit/docx-redline-composer.test.tsx`, green); typecheck clean; Codex-reviewed.
**Known follow-up (logged, lower priority):** `useActiveEgressProvider` resolves by localStorage key *presence* (anthropic > openai > google), while `redlineKey` requires `isValid`. Edge case: a user with a stale/invalid Anthropic key in localStorage **plus** a valid OpenAI key → hook returns 'anthropic', redline stays disabled. Acceptable for now (it matches the trust bar's behaviour exactly, so indicators still agree); the proper fix is to make the shared resolver prefer a *valid* key, which touches the trust bar too — track separately, don't fork the resolution here.
**Confirm:** re-drive E4 on Windows after deploy — "Suggest changes" enabled, run a redline, tracked changes appear.

## BUG-010 — M365 sign-in unusable on Windows (browser never opened + redirect never returned)  ·  Severity: Important (ship-blocker for Windows email)  ·  🟢 FIXED + CONFIRMED LIVE 2026-06-20
**Outcome:** after both fixes below, drove it end-to-end on the Legion: clicked Connect → Chrome opened the real Microsoft sign-in → Jameson completed his passkey → the tab showed the app's own "Signed in. You can close this tab and return to Keepance." → token stored → **real Outlook mail imported (count climbed 84 → 144 → 194 → …).** This was two independent bugs stacked:
- **(1) Browser never opened.** `util::proc::open_url` used `rundll32.exe url.dll,FileProtocolHandler <url>` (`CREATE_NO_WINDOW`) — a deprecated opener that silently failed to launch the default browser (reproduced: it opened nothing). The `open` crate's `cmd /C start` was rejected by the original authors (correctly — confirmed it splits OAuth URLs on `&`: `'beta' is not recognized…`). **Fix:** call Win32 **`ShellExecuteW`** ("open" verb) — passes the URL as a real wide-string arg (no shell parsing, `&`/`%` intact), reliably opens the default browser, no console window. New dep `windows-sys` (windows-target only). Files: `src-tauri/src/util/proc.rs`, `src-tauri/Cargo.toml`.
- **(2) Redirect returned to a dead port → "localhost refused to connect".** The loopback listener bound `127.0.0.1` (IPv4), but the redirect URI used `localhost` (Microsoft personal accounts require it). On Windows `localhost` resolves to `::1` (IPv6) first, so the browser POSTed the code to `[::1]:<port>` where nothing listened → the user saw "localhost refused" and the app timed out ("timed out waiting for OAuth redirect"). **Fix:** bind the listener to the literal **`localhost`** (new `bind_loopback_host("localhost")`), so tokio resolves it to the SAME address the browser will — they always meet. Gmail keeps `127.0.0.1` (it already matched). Files: `src-tauri/src/commands/mail/gmail/oauth.rs`, `src-tauri/src/commands/mail/mod.rs`.

**Original symptom + investigation (kept for the record):**
**Found + CONFIRMED live by Jameson (2026-06-20)** on the Legion: clicking **Reconnect** (and the same code path for first-time **Connect Microsoft 365**) does nothing visible — no browser/sign-in page opens — and after the OAuth wait it errors **"timed out waiting for OAuth."** Reproduced the symptom remotely (button stuck "Reconnecting…", loopback listener bound, no browser launched).
**Root cause:** the OAuth flow (`outlook_connect`, and the Gmail/`gmail_connect` path too) opens the system browser via `open_browser` → `crate::util::proc::open_url` → on Windows `rundll32.exe url.dll,FileProtocolHandler <url>` with `CREATE_NO_WINDOW`. `rundll32 ... FileProtocolHandler` is a long-deprecated, unreliable way to open a URL — it fails silently with some default browsers / configurations (here the default browser is **Vivaldi**). When it fails, the loopback listener just waits 300s and the user sees nothing, then a timeout. The non-Windows branch already uses the reliable `open::that` crate; only the Windows branch uses the bad method.
**Impact:** a real Windows customer whose default browser/config trips this sees "Connect Microsoft 365" (and Gmail/IMAP) do nothing — the email feature is unreachable for them. High-value, customer-facing.
**Workaround (works today):** the **device-code flow** — `mail_begin_login` returns a short code + `login.microsoft.com/device`; the user signs in on ANY device (their own machine/phone, where the passkey + password manager live) and the desktop polls `mail_poll_login` for the token. Verified working for the personal `@outlook.com` account (despite a code comment implying loopback "replaced" device-code). This is also the *better UX for a remote/headless machine*, since nothing needs to open locally.
**Fix plan:** (a) replace the Windows branch of `open_url` with a reliable opener — `open::that(url)` (same crate the other branch uses) or `ShellExecuteW`/the Tauri opener plugin — and **surface a real error** if the launch fails instead of silently waiting; (b) add a **manual fallback in the connector UI**: if the browser doesn't open (or always), show the auth URL with a "Copy link" button, AND/OR expose the device-code option ("can't open a browser? use a sign-in code") so a stuck user has a way through; (c) put a timeout/clear-error on the OAuth wait so "timed out waiting for OAuth" becomes actionable ("we couldn't open your browser — copy this link / use a code"). Reproduce cleanly (close the browser first, then test rundll32 vs ShellExecute) before/with the fix; add a unit/integration check where feasible.
**Confirm:** after the fix, clicking Connect opens the sign-in reliably on a Vivaldi-default Windows machine; the fallback path works when it can't.
