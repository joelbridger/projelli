But it then **stays "Syncing…" for 2.5+ minutes with 0 emails imported, no error message, no timeout, and no "reconnect" prompt.** No alert/toast anywhere. ## BUG-010 — M365 sign-in unusable on Windows (browser never opened + redirect never returned)  ·  Severity: Important (ship-blocker for Windows email)  ·  🟢 FIXED + CONFIRMED LIVE 2026-06-20
**Outcome:** after both fixes below, drove it end-to-end on the Legion: clicked Connect → Chrome opened the real Microsoft sign-in → Jameson completed his passkey → the tab showed the app's own "Signed in. You can close this tab and return to Keepance." → token stored → **real Outlook mail imported (count climbed 84 → 144 → 194 → …).** This was two independent bugs stacked:
- **(1) Browser never opened.** `util::proc::open_url` used `rundll32.exe url.dll,FileProtocolHandler <url>` (`CREATE_NO_WINDOW`) — a deprecated opener that silently failed to launch the default browser (reproduced: it opened nothing). The `open` crate's `cmd /C start` was rejected by the original authors (correctly — confirmed it splits OAuth URLs on `&`: `'beta' is not recognized…`). **Fix:** call Win32 **`ShellExecuteW`** ("open" verb) — passes the URL as a real wide-string arg (no shell parsing, `&`/`%` intact), reliably opens the default browser, no console window. New dep `windows-sys` (windows-target only). Files: `src-tauri/src/util/proc.rs`, `src-tauri/Cargo.toml`.
- **(2) Redirect returned to a dead port → "localhost refused to connect".** The loopback listener bound `127.0.0.1` (IPv4), but the redirect URI used `localhost` (Microsoft personal accounts require it). On Windows `localhost` resolves to `::1` (IPv6) first, so the browser POSTed the code to `[::1]:<port>` where nothing listened → the user saw "localhost refused" and the app timed out ("timed out waiting for OAuth redirect"). **Fix:** bind the listener to the literal **`localhost`** (new `bind_loopback_host("localhost")`), so tokio resolves it to the SAME address the browser will — they always meet. Gmail keeps `127.0.0.1` (it already matched). Files: `src-tauri/src/commands/mail/gmail/oauth.rs`, `src-tauri/src/commands/mail/mod.rs`.

**Original symptom + investigation (kept for the record):**
**Found + CONFIRMED live by Jameson (2026-06-20)** on the Legion: clicking **Reconnect** (and the same code path for first-time **Connect Microsoft 365**) does nothing visible — no browser/sign-in page opens — and after the OAuth wait it errors **"timed out waiting for OAuth."** Reproduced the symptom remotely (button stuck "Reconnecting…", loopback listener bound, no browser launched).
**Root cause:** the OAuth flow (`outlook_connect`, and the Gmail/`gmail_connect` path too) opens the system browser via `open_browser` → `crate::util::proc::open_url` → on Windows `rundll32.exe url.dll,FileProtocolHandler <url>` with `CREATE_NO_WINDOW`. `rundll32 ... FileProtocolHandler` is a long-deprecated, unreliable way to open a URL — it fails silently with some default browsers / configurations (here the default browser is **Vivaldi**). When it fails, the loopback listener just waits 300s and the user sees nothing, then a timeout. The non-Windows branch already uses the reliable `open::that` crate; only the Windows branch uses the bad method.
**Impact:** a real Windows customer whose default browser/config trips this sees "Connect Microsoft 365" (and Gmail/IMAP) do nothing — the email feature is unreachable for them. High-value, customer-facing.
**Workaround (works today):** the **device-code flow** — `mail_begin_login` returns a short code + `login.microsoft.com/device`; the user signs in on ANY device (their own machine/phone, where the passkey + password manager live) and the desktop polls `mail_poll_login` for the token. Verified working for the personal `@outlook.com` account (despite a code comment implying loopback "replaced" device-code). This is also the *better UX for a remote/headless machine*, since nothing needs to open locally.
**Fix plan:** (a) replace the Windows branch of `open_url` with a reliable opener — `open::that(url)` (same crate the other branch uses) or `ShellExecuteW`/the Tauri opener plugin — and **surface a real error** if the launch fails instead of silently waiting; (b) add a **manual fallback in the connector UI**: if the browser doesn't open (or always), show the auth URL with a "Copy link" button, AND/OR expose the device-code option ("can't open a browser? use a sign-in code") so a stuck user has a way through; (c) put a timeout/clear-error on the OAuth wait so "timed out waiting for OAuth" becomes actionable ("we couldn't open your browser — copy this link / use a code"). Reproduce cleanly (close the browser first, then test rundll32 vs ShellExecute) before/with the fix; add a unit/integration check where feasible.
**Confirm:** after the fix, clicking Connect opens the sign-in reliably on a Vivaldi-default Windows machine; the fallback path works when it can't.

## BUG-011 — App crashes (allocation-failure abort) during a large mail import  ·  Severity: Important (data-loss / crash) · 🟢 FIXED + CONFIRMED LIVE 2026-06-20
**FIX:** root cause was `spawn_mail_rag_index` (the per-message RAG indexer used as the sync `index_callback`): it did a fire-and-forget `tokio::spawn` for EVERY message with NO concurrency cap. A large mailbox arriving faster than embedding completes spawned thousands of simultaneous embedding tasks (each driving CPU-heavy ONNX inference, which spawns its own inference threads) → memory/thread exhaustion → allocation failure → abort. Added a global `static MAIL_INDEX_SEMAPHORE: tokio::sync::Semaphore::const_new(4)` that every spawned indexer `acquire().await`s before doing heavy work, so at most 4 embeddings run concurrently and the rest queue cheaply (holding only their text). `src-tauri/src/commands/mail/mod.rs`. **Verified live (2026-06-20):** re-ran the same large-mailbox import — it sailed PAST the previous ~1,400 crash point to 4,000+ messages with the app staying alive and responsive (before: hard crash around there). Root-caused independently + confirmed in code.

### Original investigation (kept for the record)
**Found live (2026-06-20)** right after BUG-010 was fixed: with the Outlook sign-in working, a real import of Jameson's mailbox ran and mail flowed in (84 → … → ~1,400 messages over a few minutes), then the **whole app process exited/crashed**. `C:\tauri-dev.log` shows repeated `memory allocation of <N> bytes failed` then `process didn't exit successfully: target\debug\keepance.exe (exit code: 0xc0000409, STATUS_STACK_BUFFER_OVERRUN)` — i.e. Rust's allocation-failure → `handle_alloc_error` → abort.
**Why it's probably a real bug, not "low RAM":** the machine had **22.6 GB free of 31 GB** at the time. A 64-bit process failing allocations with 22 GB free points to either an **integer-overflow in an allocation size** (the logged byte counts are garbled/huge — interleaved thread output around `32768`, with fragments like `3276832768` ≈ 3 GB and `327683276832768` ≈ 327 TB), **unbounded buffering** (e.g. loading too much into memory at once during indexing), or **thread/stack exhaustion** (the abort code is the stack-overrun status). Needs proper root-causing.
**Caveats:** this was the **dev/debug build** (no optimizations, higher memory use) and a sizeable mailbox (his real Outlook ≈ 5,425 messages, each RAG-indexed = embeddings). A release build may not hit it — but a crash mid-import is serious (a real customer with a big mailbox could lose the app and a partial/corrupt index).
**Investigation plan:** (a) inspect the mail import + RAG-indexing path (`commands/mail/sync.rs`, `commands/rag/*`, embedding batching) for an overflowing size computation, an all-at-once load, or unbounded concurrency/threads; (b) check whether the embedding/index step batches with a bounded buffer; (c) reproduce with a capped import (`IMPORT_FOLDER_CAP`) + watch process memory to see if it grows unboundedly vs. spikes; (d) confirm on a release build whether it still crashes; (e) ensure a crash mid-import leaves a recoverable (not corrupt) index. Dispatching an independent (Codex) read-only investigation of the allocation path.
**Note:** does NOT undermine BUG-010 — the sign-in + import pipeline are proven working (mail imported successfully up to the crash). This is a scale/robustness bug in the import itself.

## BUG-016 — AI fabricates a confident answer + a fake citation for content not in the corpus  ·  Severity: Important (trust, core promise)  ·  🟢 FIXED + CONFIRMED LIVE

**RESOLUTION (2026-06-20) — TDD + two adversarial Codex reviews + live bench drive.** The fix has five layers, all in the Ask pipeline (frontend):
1. **Retrieval-evidence gate** (`useAsk.ts`) — when indexing is on but retrieval returns nothing in scope, Ask declines with a fixed message ("I couldn't find anything about that in your documents.") *before* calling the model, so it can't free-associate.
2. **Hardened answer prompt** (`useAsk.ts`) — answer ONLY from the context block; decline with that exact wording when the context lacks the answer; never state a figure/date/name or cite a source not in the context.
3. **Exact-locator citation grounding** (`useAsk.ts`, two-pass) — a citation is kept (chip + counts toward the banner) ONLY if it matches an actual retrieved chunk by file AND locator (paragraph for text, page for PDF). Drops both "file not retrieved" and "real file but a paragraph/page never retrieved" — a real filename can't launder a fabricated claim. Dropped markers are stripped from the prose. Excerpt/locator come from the matched chunk, never the model text.
4. **Banner gate** (`TurnBlock.tsx`) — "Answered over your own files" (and the mutually-exclusive "Not cited" warning) gate on a *grounded* citation surviving, not on `citations.length`.
5. **Re-ground on reload** (`askHelpers.ts reconstructTurns`) + **page-aware shared resolution** (`workspaceCommand.ts parseCitations`/`resolveCitationPath`/`verifyCitations`, `renderingHelpers.tsx`) — a turn saved before the fix is re-checked against its own saved sources on restore (so a stale bad answer can't re-render fake/green); `[file.pdf page N]` now parses and resolves by page number on both Ask and Chat surfaces.

**Deliberately NOT done:** an absolute similarity-score floor — with the e5 embedding model's compressed score range (LanceDB score = (1+cosine)/2; even unrelated text scores ≈0.85–0.89, relevant ≈0.92), a threshold can't separate off-corpus from real without dropping real answers. Exact-locator grounding + prompt hardening is the regression-safe mechanism.

**Tests:** `tests/unit/ask/bug016-ask-grounding.test.tsx` (empty-retrieval decline, fake-file drop, real-file-wrong-paragraph drop, PDF page+paragraph grounding, regression-guard real answer, reconstruct re-grounding) + a `page N` case in `tests/unit/workspace-command.test.ts`. Full suite green (3423), typecheck clean.

**Live bench confirmation (real OpenAI model, KeepanceTest workspace):** PURPLEWHALE → declines, no fabrication, no banner; GEICO auto-pay "$100.65" → green banner + chip + Verify ENABLED; Garcia "July 14, 2026" → cited. A deliberately mis-worded GEICO question ("tender") declined rather than forcing the auto-pay figure into a "tender" claim.

## BUG-013 — Email viewer doesn't show which matter an email is already filed to  ·  Severity: Minor (UX) → became a durability fix  ·  🟢 FIXED + CONFIRMED LIVE

**RESOLUTION (2026-06-21) — full DURABLE rework, no shortcuts (Jameson's directive), 3 adversarial Codex passes + live bench.** Investigation found the backlog's plan ("read message.matterId") was impossible — neither `mail_get_message` nor the list query carried the matter; it lived only in the rebuildable RAG index, so filing wasn't durable (a re-sync re-stamped the folder matter and wiped a manual filing). The robust fix makes the **encrypted mail DB the source of truth**:
1. **Durable per-message override** in the mail DB's `meta` table (`get/set/clear_message_matter`, keyed `matter:<id>`), which sync's `messages` upsert never touches. (`mail/store.rs`)
2. **Filing** (`mail_retag_message_matter`) writes that override FIRST (the success criterion — no more false "filed" when nothing was stored; guards against filing a non-existent message) then best-effort mirrors to the RAG index.
3. **Viewer** (`get_message_with_key`→`MailView.matterId`) reads the override (source of truth), filtering the `unassigned` sentinel/empty → "not filed"; `mail_get_message` falls back to the folder-level matter in the RAG index only when there's no override.
4. **Survives re-indexing:** sync (`apply_messages_enc`), backfill (`mail_backfill_rag`), AND folder-remap (`mail_retag_folder_matter`) all resolve the per-message override before the folder mapping, so a manual filing is never clobbered.
5. **`matter_for_path`** scans all chunks and returns the single agreed matter (None if none/disagree) — no arbitrary pick.
6. **UI:** persistent "Filed to {matter}" indicator + selected button + immediate reflect on (re-)file; an email filed to an archived/removed matter still discloses it's filed.

**Tests:** `mail/store.rs` (override survives an upsert of the same message + survives close/reopen — the durability guarantee), `tests/rag_matter_scope.rs` (`matter_for_path` reads/follows retag/None), `tests/unit/mail/EmailViewer.test.tsx` (filed/unfiled/immediate-reflect). cargo check + 186 mail tests + full vitest (3426) green.

**Live bench (real Windows, 2026-06-21):** opened a real email — unfiled showed NO filed indicator (the `unassigned` fix); filed it to the Garcia matter → "Filed to Roberto Garcia…" + button selected; navigated away and reopened → STILL "Filed to Roberto Garcia…" (durable read from the mail DB). **Known follow-ups (not blocking, noted by Codex):** explicit "unfile from a mapped folder" (suppress the folder fallback) is a future feature; `MailListItem` has no `matterId` yet so the email LIST rows don't show filed state (the viewer — the reported bug — does).

### Original report (kept for the record)
**Found driving H7 on real Windows (2026-06-20).** Filing an email to a matter works and persists (`mailRetagMessageMatter`), both single and bulk. But when you **reopen** a filed email, the viewer shows no indication it's already filed — the green "Filed successfully." line is a transient per-session flag (`fileSuccess` in `EmailViewer.tsx` ~line 494), and the matter buttons (`file-to-matter-btn-${m.id}`) are rendered identically for every matter with no "currently filed to X" / selected state. Confirmed by a differential check: an email filed individually and one filed in bulk both show the exact same "File to matter | Roberto Garcia…" UI as an unfiled one.
**Impact:** for a matter-centric, privilege-sensitive product, a lawyer reopening an email can't tell whether (or to which matter) it's filed, can't unfile it, and could silently re-file it elsewhere. Low severity (filing itself works) but a real gap in the trust/organization story.
**Fix plan:** surface the message's current matter association in the viewer — read `message.matterId` (it's set by the retag) and (a) mark the current matter's button as selected/checked, (b) show "Filed to {matter}" with an unfile/change affordance, instead of relying on the transient `fileSuccess`. Add a unit/RTL test that a message with a `matterId` renders its matter as selected. Not fixed this session (touches the viewer's data flow + the message shape passed in); logged so it isn't lost.

## BUG-012 — Markdown/text inline "Ask AI" edit is dead for EVERY user (no provider wired)  ·  Severity: Important  ·  🟢 fixed (committed 9cda082, re-verified live)
**Found + CONFIRMED on real Windows (2026-06-20)** while driving E7 (inline AI edit on a `.md` file). Opened `fee-agreement.md`, selected a word → the "Ask AI" anchor appeared correctly → typed an instruction → clicked Ask. The input collapsed (submit fired) but **nothing happened: no streamed change, no diff overlay, no error, no toast.** The feature is completely non-functional.
**Impact:** the inline "Ask AI" edit on Markdown/plain-text documents (E7/E8 — a documented editing feature) does nothing for **every** user, regardless of provider. Broader than BUG-009 (which only hit non-Anthropic users): here the provider is null for everyone. And it fails **silently**, so a user just thinks the AI ignored them.
**Root cause (confirmed in code):** `src/app/shell/layout/MainPanel.tsx` renders `<MarkdownEditor>` **without a `getAiProvider` prop**. `MarkdownEditor` passes `getProvider: () => getAiProviderRef.current?.() ?? null` to `useInlineAiEdit`; with the prop absent it's always `null`. In `useInlineAiEdit.ts` (~line 181) the submit handler does `const provider = getProvider(); if (!provider || !provider.sendMessageStreaming) { return; }` — a silent early return (the code comment literally says *"We could show a toast here; for now just abort gracefully."*). So: no provider → silent no-op. Same MainPanel-didn't-wire-the-editor family as BUG-009 (DocxEditor), but here nothing at all was passed.
**Fix (applied, uncommitted):** added a small pure helper `src/app/shell/layout/resolveInlineEditProvider.ts` that turns the already-resolved provider id (`redlineProvider`, from `resolveRedlineProvider` + `useActiveEgressProvider` — the single source the trust bar/redline use) plus the user's `apiKeys` into a concrete `Provider` via the shared `createProvider` factory: local (`ollama`) built keyless; cloud built BYOK only when a VALID key exists for that provider; otherwise `null` (so it degrades cleanly instead of constructing a keyless cloud provider that 401s mid-stream). `MainPanel` now passes `getAiProvider={() => resolveInlineEditProvider({ provider: redlineProvider, apiKeys, ...(Local-only ? { model: redlineOllamaModel } : {}) })}` to `MarkdownEditor`. 5 unit tests (`tests/unit/inline-edit-provider.test.ts`, green); typecheck clean.
**Known follow-up (logged, lower priority) — BUG-012b:** even with the provider wired, `useInlineAiEdit`'s null-provider branch still returns **silently**. A user in Local-only mode with no Ollama running, or with no valid key, gets no feedback. Should surface a minimal message ("Add an AI key in Settings to use inline edit" / "Start your local model"). Touches the hook + anchor UI; deferred so this fix stays scoped to the actual feature-dead bug. (Mirrors BUG-009's deferred resolver-validity follow-up.)
