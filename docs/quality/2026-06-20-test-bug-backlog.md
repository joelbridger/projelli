## BUG-010 — M365 sign-in unusable on Windows (browser never opened + redirect never returned)  ·  Severity: Important (ship-blocker for Windows email)  ·  🟢 FIXED + CONFIRMED LIVE 2026-06-20
**Outcome:** after both fixes below, drove it end-to-end on the Legion: clicked Connect → Chrome opened the real Microsoft sign-in → Jameson completed his passkey → the tab showed the app's own "Signed in. You can close this tab and return to Keepance." → token stored → **real Outlook mail imported (count climbed 84 → 144 → 194 → …).** This was two independent bugs stacked:
- **(1) Browser never opened.** `util::proc::open_url` used `rundll32.exe url.dll,FileProtocolHandler <url>` (`CREATE_NO_WINDOW`) — a deprecated opener that silently failed to launch the default browser (reproduced: it opened nothing). The `open` crate's `cmd /C start` was rejected by the original authors (correctly — confirmed it splits OAuth URLs on `&`: `'beta' is not recognized…`). **Fix:** call Win32 **`ShellExecuteW`** ("open" verb) — passes the URL as a real wide-string arg (no shell parsing, `&`/`%` intact), reliably opens the default browser, no console window. New dep `windows-sys` (windows-target only). Files: `src-tauri/src/util/proc.rs`, `src-tauri/Cargo.toml`.
- **(2) Redirect returned to a dead port → "localhost refused to connect".** The loopback listener bound `127.0.0.1` (IPv4), but the redirect URI used `localhost` (Microsoft personal accounts require it). On Windows `localhost` resolves to `::1` (IPv6) first, so the browser POSTed the code to `[::1]:<port>` where nothing listened → the user saw "localhost refused" and the app timed out ("timed out waiting for OAuth redirect"). **Fix:** bind the listener to the literal **`localhost`** (new `bind_loopback_host("localhost")`), so tokio resolves it to the SAME address the browser will — they always meet. Gmail keeps `127.0.0.1` (it already matched). Files: `src-tauri/src/commands/mail/gmail/oauth.rs`, `src-tauri/src/commands/mail/mod.rs`.

**Original symptom + investigation (kept for the record):**
**Found + CONFIRMED live by Jameson (2026-06-20)** on the Legion: clicking **Reconnect** (and the same code path for first-time **Connect Microsoft 365**) does nothing visible — no browser/sign-in page opens — and after the OAuth wait it errors **"timed out waiting for OAuth."** Reproduced the symptom remotely (button stuck "Reconnecting…", loopback listener bound, no browser launched).
**Root cause:** the OAuth flow (`outlook_connect`, and the Gmail/`gmail_connect` path too) opens the system browser via `open_browser` → `crate::util::proc::open_url` → on Windows `rundll32.exe url.dll,FileProtocolHandler <url>` with `CREATE_NO_WINDOW`. `rundll32 ... FileProtocolHandler` is a long-deprecated, unreliable way to open a URL — it fails silently with some default browsers / configurations (here the default browser is **Vivaldi**). When it fails, the loopback listener just waits 300s and the user sees nothing, then a timeout. The non-Windows branch already uses the reliable `open::that` crate; only the Windows branch uses the bad method.
**Impact:** a real Windows customer whose default browser/config trips this sees "Connect Microsoft 365" (and Gmail/IMAP) do nothing — the email feature is unreachable for them. High-value, customer-facing.
**Workaround (works today):** the **device-code flow** — `mail_begin_login` returns a short code + `login.microsoft.com/device`; the user signs in on ANY device (their own machine/phone, where the passkey + password manager live) and the desktop polls `mail_poll_login` for the token. Verified working for the personal `@outlook.com` account (despite a code comment implying loopback "replaced" device-code). This is also the *better UX for a remote/headless machine*, since nothing needs to open locally.
**Fix plan:** (a) replace the Windows branch of `open_url` with a reliable opener — `open::that(url)` (same crate the other branch uses) or `ShellExecuteW`/the Tauri opener plugin — and **surface a real error** if the launch fails instead of silently waiting; (b) add a **manual fallback in the connector UI**: if the browser doesn't open (or always), show the auth URL with a "Copy link" button, AND/OR expose the device-code option ("can't open a browser? use a sign-in code") so a stuck user has a way through; (c) put a timeout/clear-error on the OAuth wait so "timed out waiting for OAuth" becomes actionable ("we couldn't open your browser — copy this link / use a code"). Reproduce cleanly (close the browser first, then test rundll32 vs ShellExecute) before/with the fix; add a unit/integration check where feasible.
**Confirm:** after the fix, clicking Connect opens the sign-in reliably on a Vivaldi-default Windows machine; the fallback path works when it can't.

## BUG-011 — App crashes (allocation-failure abort) during a large mail import  ·  Severity: Important (data-loss / crash) · 🟢 FIXED + CONFIRMED LIVE 2026-06-20
**FIX:** root cause was `spawn_mail_rag_index` (the per-message RAG indexer used as the sync `index_callback`): it did a fire-and-forget `tokio::spawn` for EVERY message with NO concurrency cap. A large mailbox arriving faster than embedding completes spawned thousands of simultaneous embedding tasks (each driving CPU-heavy ONNX inference, which spawns its own inference threads) → memory/thread exhaustion → allocation failure → abort. ## BUG-016 — AI fabricates a confident answer + a fake citation for content not in the corpus  ·  Severity: Important (trust, core promise)  ·  🟢 FIXED + CONFIRMED LIVE

**RESOLUTION (2026-06-20) — TDD + two adversarial Codex reviews + live bench drive.** The fix has five layers, all in the Ask pipeline (frontend):
1. **Retrieval-evidence gate** (`useAsk.ts`) — when indexing is on but retrieval returns nothing in scope, Ask declines with a fixed message ("I couldn't find anything about that in your documents.") *before* calling the model, so it can't free-associate.
2. **Hardened answer prompt** (`useAsk.ts`) — answer ONLY from the context block; decline with that exact wording when the context lacks the answer; never state a figure/date/name or cite a source not in the context.
3. **Exact-locator citation grounding** (`useAsk.ts`, two-pass) — a citation is kept (chip + counts toward the banner) ONLY if it matches an actual retrieved chunk by file AND locator (paragraph for text, page for PDF). Drops both "file not retrieved" and "real file but a paragraph/page never retrieved" — a real filename can't launder a fabricated claim. Dropped markers are stripped from the prose. Excerpt/locator come from the matched chunk, never the model text.
4. **Banner gate** (`TurnBlock.tsx`) — "Answered over your own files" (and the mutually-exclusive "Not cited" warning) gate on a *grounded* citation surviving, not on `citations.length`.
5. **Re-ground on reload** (`askHelpers.ts reconstructTurns`) + **page-aware shared resolution** (`workspaceCommand.ts parseCitations`/`resolveCitationPath`/`verifyCitations`, `renderingHelpers.tsx`) — a turn saved before the fix is re-checked against its own saved sources on restore (so a stale bad answer can't re-render fake/green); `[file.pdf page N]` now parses and resolves by page number on both Ask and Chat surfaces.

**Deliberately NOT done:** an absolute similarity-score floor — with the e5 embedding model's compressed score range (LanceDB score = (1+cosine)/2; even unrelated text scores ≈0.85–0.89, relevant ≈0.92), a threshold can't separate off-corpus from real without dropping real answers. Exact-locator grounding + prompt hardening is the regression-safe mechanism.

**Tests:** `tests/unit/ask/bug016-ask-grounding.test.tsx` (empty-retrieval decline, fake-file drop, real-file-wrong-paragraph drop, PDF page+paragraph grounding, regression-guard real answer, reconstruct re-grounding) + a `page N` case in `tests/unit/workspace-command.test.ts`. ## Matter-isolation audit (2026-06-21, Codex adversarial read-only)

The product's core promise is matter-scoped confidentiality ("one client's data can never surface inside another matter"). A dedicated Codex audit confirmed the **RAG retrieval path is genuinely isolated at the DATABASE level** (`rag_retrieve` applies a matter `only_if(...)` predicate before LanceDB search; matter IDs are validated + SQL-escaped; email/document type filters layer AFTER the matter filter; citation verify checks chunk-id + matter-id and reports mismatch). But it found that **isolation is enforced for retrieval and NOT for the other ways content reaches the model**. Threat-model note: for a SOLO user every matter is their own data on their own machine under their own BYOK key, so these are confidentiality-*discipline*/promise gaps, not third-party breaches; for the FIRM tier with ethical walls (BUG-041) they can be a real wall breach.

- **BUG-036 — Chat file tools bypassed matter scope (Codex: Critical).**  🟢 **FIXED (2026-06-21).** The cloud-chat file tools (`read_file`/`list_files`/`search_files`/`write_file`/`move_file`/`delete_file`) only checked `startsWith(rootPath)`, so a chat scoped to Matter B could read/search/write Matter A's files. New shared guard `src/platform/matter/matterScopeGuard.ts` `pathInMatterScope(absPath, activeMatterId, matters)` (null id = all-matters = unrestricted; else path must `resolveMatterId` to the active matter). `useChatSending.ts` toolExecutor now THROWS on cross-matter read/write/create/move(both paths)/delete and FILTERS list/search results to the active matter. Matches retrieval scoping exactly; all-matters chats stay workspace-wide. **Codex re-review hardened it:** tool scope is now taken from the SAME scope captured at send start (not a fresh read, so a mid-response matter switch can't widen it); the guard fails closed on any `..` traversal; and `list_files` still shows ANCESTOR folders of the active matter so the model can navigate down into a nested matter (only siblings/other matters are hidden). Test `tests/unit/matter/matter-scope-guard.test.ts` (7 cases incl. nested-mapping, no-folders, and `..` traversal).
- **BUG-037 — Open editor files injected across matters (Codex: Critical).**  🟢 **FIXED (2026-06-21).** `AIChatViewer` `scopedOpenFiles` was filtered only by the optional folder scope, so a Matter A doc open in a tab could be sent into a Matter B chat. Now, when a matter is active, open files are first filtered to that matter via the shared `pathInMatterScope` (then the folder scope narrows further). All-matters keeps every open file. Same shared guard + test as BUG-036. (Codex re-review #6: the `?testMode=true` prompt helper now also uses the matter-scoped open-file set, so tests inspect the real prompt.)
- **BUG-038 — MCP read/search is whole-workspace, not matter-scoped (Codex: High).**  🔴 OPEN. External MCP clients can list/read all workspace files and `search_workspace` passes `None` matter scope (searches all matters). Architecturally heavier — the MCP sidecar has no "active matter" session concept; needs a matter-aware session scope (default: no cross-matter unless explicitly granted). Flagged for a focused effort (may want Jameson's input on the intended firm/MCP behavior).
- **BUG-039 — "Network lockdown" only blocks MCP WRITES, not reads/search (Codex: High).**  🔴 OPEN. Privileged-matter "network lockdown" UI/comments say MCP is disabled, but the gate only auto-denies write approvals; read/search/list tools need no approval and still run. - **BUG-040 — Deleted-matter chunks remained searchable via All-Matters (Codex: High).**  🟡 **PARTIAL (2026-06-21) — defense-in-depth done; permanent scrub is a product decision (BUG-042).** Only `rag_delete_path` (path-level) existed, so a deleted matter's CURRENT chunks survived and all-matters retrieval (no matter filter) could still surface them. Added `store::delete_matter(table, matter_id)` (validate + SQL-escape + `table.delete("matter_id = '..'")`; refuses the UNASSIGNED bucket) + `rag_delete_matter` Tauri command (registered in lib.rs) + JS `ragDeleteMatter`, called fire-and-forget in `matterStore.deleteMatter`. The immediate purge is real + valuable (stops the stale-matter-scope surface), but a full guarantee needs BUG-042.
- **BUG-042 — Matter-deletion content semantics (product decision).**  🟢 **DECIDED + DONE (2026-06-21).** Jameson's call: **Delete = remove the matter + wipe the AI's memory of it, but KEEP the user's files.** (Archive already covers "hide but keep everything"; Delete is the more final one that never destroys documents — a law practice has retention duties. To make content truly disappear the user deletes the files themselves.) Implemented the data gap, then **independently Codex-reviewed and hardened**. On delete, every email's durable per-message "filed to this matter" override is re-filed as an explicit **`UNASSIGNED_MATTER` tombstone** (NOT just deleted). New Rust `EncryptedMailStore::clear_message_matter_for_matter(matter_id) -> usize` (`UPDATE meta SET value='unassigned' WHERE key LIKE 'matter:%' AND value=?`; scoped to the override family + value match, never any other `meta` row) + `mail_clear_matter_filings` Tauri command (registered in lib.rs; no-op if no mail DB on disk) + JS `mailClearMatterFilings`, called fire-and-forget alongside `ragDeleteMatter` in `matterStore.deleteMatter`. **Why a tombstone, not a delete (Codex review Finding #1, High — the leak it prevents):** a plain delete would make the next sync fall back to the email's FOLDER matter, so an email filed to deleted matter A but living in a folder mapped to a different LIVE matter B would *silently move into B*. For a legal tool that must never happen. Centralized the resolution in one helper `resolve_effective_matter(override, folder_default)` (real override wins → BUG-013; explicit `unassigned` tombstone stays unassigned, NOT re-absorbed into the folder → BUG-042; else folder default) and routed all three RAG-index sites through it (`sync.rs` apply_messages_enc, `mod.rs` folder-remap retag, `mod.rs` backfill); the viewer already treated a non-real override as unassigned. Tests: Rust `enc_clear_message_matter_for_matter_tombstones_only_that_matters_filings` (tombstones only the target matter, leaves other matters + unrelated meta untouched, idempotent) + `resolve_effective_matter` 3-state unit tests (real-wins / no-override-folder / tombstone-stays-unassigned) + frontend wiring asserts in `matter-delete-rag-purge.test.ts` (4). Full mail cargo suite green (190). The delete-confirm message ("Your files stay on your computer, but this matter's folder and email mappings, notes, and saved state are cleared") is now honest — files stay (and re-index as 'unassigned' since they remain in the workspace, which is correct), the AI traces (RAG chunks + email filings) are cleared and the emails become unassigned, never another matter's. **Intentionally NOT done** (would be wrong behavior, not a gap): deleting the on-disk files, or tombstoning folders so re-index can't re-add them — a file in the workspace SHOULD be searchable; forcing it invisible while on disk is incoherent. **Tracked residual (Codex Finding #2, Med — durability, not a leak):** the cleanups (this + BUG-040's RAG purge) are fire-and-forget; if the mail tombstone UPDATE itself fails (e.g. DB locked beyond the busy timeout), the override stays the deleted matter id and the next sync re-tags the email as a phantom of the gone matter, with no auto-retry. The robust hardening is a durable retry-until-success cleanup (or a startup reconciliation that tombstones any override whose matter id is no longer in the live matter list) — a scoped reliability follow-up shared with BUG-040, not built now. The common path (cleanup succeeds) has no phantom and no cross-matter leak.
- **BUG-041 — Ethical-wall revocation: cached local key/chunks can survive (Codex: High, firm tier).**  🔴 OPEN. Walled users are correctly skipped for new key distribution, but `obtainMatterKey` returns a cached LOCAL key before checking the server, and local RAG chunks aren't tied to firm authorization — so a walled associate's device may still surface old Matter A content locally. Fix: on wall/remove/access-loss, clear local matter keys, stop sync, lock/remove the local matter, and purge that matter's RAG rows; retrieval should refuse shared matters when current firm access/key status is missing. Firm-crypto, high-stakes — needs careful design (likely Jameson input on intended firm behavior).

### BUG-098 — Windows: EVERY grounded answer rendered "Not cited from your files" (headline feature broken) 🟢 TS FIX SHIPPED + LIVE; 🟠 Rust root-cause IN PROGRESS (found LIVE on Windows, 2026-06-22)

**Root cause (two layers, both Windows-only — why the green unit suite missed it: tests use clean forward-slash paths with no duplicates):**
The RAG store holds the SAME physical document twice under two path spellings that differ only in separators: a mixed `C:/KeepanceTest\fee-agreement.md` (full-workspace index: forward-slash root + backslash children) and an all-backslash `C:\KeepanceTest\fee-agreement.md` (file watcher's native OS path). Both persist as distinct source keys (the store hashes/tokens/deletes by the exact string), and each indexing path only refreshes its own spelling, so the duplication is re-created every run — not stale data. Consequences: (a) `resolveCitationTarget` saw two "different" paths for one file → `uniquePaths.size > 1` → treated it as an ambiguous cross-folder basename collision → dropped EVERY citation → "Not cited"; (b) each file occupies two top-K slots (token-doubling + crowding real docs out — this is why a 2-part question's deadline half hallucinated: `matter-summary.md` got crowded out). Captured live via the OpenAI request body (two source headers per file) + a direct `rag_retrieve` call (two chunks per file, distinct ids, both `matterId:"unassigned"`).

- **Layer 1 — TS citation resolver (SHIPPED + LIVE-VERIFIED):** `resolveCitationTarget` (`src/platform/rag/workspaceCommand.ts`) now separator-normalizes paths when computing `uniquePaths`, so the phantom duplicate collapses to one source and the citation resolves; a genuine cross-folder collision (`a/dup.md` vs `b/dup.md`) still normalizes to two distinct paths and stays ambiguous (fail-closed preserved). TDD: 2 new red→green tests in `citation-grounding-strict.test.ts` (Windows same-file dup resolves; Windows cross-folder collision still null). Verified LIVE on the bench (Vite HMR, no rebuild): the same engagement-letter question now returns a GREEN chip `[1]`, the "Answered over your own files. - **Layer 2 — Rust store path canonicalization (ROOT CAUSE, in progress via Codex):** canonicalize document source paths at the RAG/store boundary (`canonical_source_path()` used in chunk_id / build_batch / upsert / delete / retag / matter-for-path / PDF index) so one file = one source key, and bump `INDEX_VERSION` 10→11 to trigger the existing drop-and-rebuild migration (the vector store is a rebuildable cache). This stops the duplication at the source and recovers the wasted top-K budget + tokens. Needs a Rust recompile + a bench re-index to live-confirm the dup is gone.
