### 2. [P1] Tab positions are fabricated 0-100 units, not real PDF page coordinates

`docusignAdapter.ts`'s `tab()` helper (~line 58) does `Math.round(anchor.rect.x * 100)` and sends that raw number as DocuSign's `xPosition`/`yPosition`/`width`/`height`. DocuSign's real tab positioning is in **points from the page's top-left**, scaled to the actual page size (a US Letter page is 612×792 points) — treating a 0-1 normalized rect as a 0-100 "percent" and sending it directly as points places every tab within an inch of the page corner regardless of where it was actually reviewed to be.

**Fix:** compute real point-based tab positions **before** calling the adapter, in `signatureWorkflow.ts`'s `startDocusignSignature`, where the flattened PDF bytes (`completion.bytes`, from `loadFreshCompletionEvidence`) are already available:
1. Obtain the real page dimensions (in points) for the specific page each tab anchor references, using `pdf-lib` (already a project dependency — `PDFDocument.load`, `page.getSize()` returns `{ width, height }` in points) or `pdfjs-dist` (also already used elsewhere in this codebase for W8) — your call which, prefer whichever is already imported nearby for consistency.
2. Convert each `DocusignTabAnchor` (`{ page, rect: { x, y, width, height } }`, all normalized 0-1, `y` measured from the top per the existing overlay convention — confirm this against `pdfTemplates/templateContract.ts`'s `PdfOverlayRect` doc comment before assuming) into real point coordinates: `xPosition = round(rect.x * pageWidthPoints)`, `width = round(rect.width * pageWidthPoints)`, and for `yPosition` account for DocuSign's coordinate origin (DocuSign's `yPosition` is also measured from the page **top**, matching the existing normalized convention — verify this rather than assuming, since a flipped Y axis would place tabs at the wrong vertical position even with correct horizontal placement): `yPosition = round(rect.y * pageHeightPoints)`, `height = round(rect.height * pageHeightPoints)`.
3. Change `DocusignEnvelopeInput.tabMap`'s type (or add a new field) so the adapter receives **already-resolved absolute point positions**, not the normalized `ReviewedDocusignTabMap` — the adapter's `tab()` helper should become a straight pass-through with no `* 100` fabrication anywhere. Update `docusignAdapter.ts` and its own test (`docusignAdapter.test.ts`) accordingly — its existing test's hardcoded expected tab values (currently asserting the old `* 100` output) need to change to real point-based expected values for a known page size.
4. Add a focused test in `signatureWorkflow.test.ts` (or a new test file) proving the point conversion is correct for at least: a US Letter page, a non-Letter page size (to prove it's not hardcoded), and a tab anchored to a specific reviewed page (not just page 1).

### 4. [P1] Signed artifacts are not encrypted at rest

`retrieveAndFileDocusignCompletion` writes the signed PDF and certificate via plain `fileIntakeDocument`/`WorkspaceService.writeFileBinary` (`intakeFiling.ts:48-76`) — the same path used for any ordinary uploaded document, which is only encrypted at rest when the user happens to have vault mode enabled for their workspace. W9-PREP §4.5.6 explicitly requires these two files to be encrypted, unconditionally (matching how `LocalSignatureRecord` is already unconditionally OS-keychain-protected via `signatureRecordStore.ts`, regardless of vault mode).

**Fix:** encrypt both files' bytes with a fresh AES-256-GCM content key before writing them via the normal filing path, so the bytes on disk are ciphertext regardless of vault backend state — reuse the existing symmetric-encryption primitives already in this codebase for exactly this shape of problem (`src/platform/intake/intakeCrypto.ts`'s content-key generation/AES-GCM helpers, already used for W8 submission chunk encryption — read that file and reuse its actual functions rather than writing new crypto). Store the raw content key (or a wrapped form of it) alongside the `LocalSignatureRecord` in `signatureRecordStore.ts`'s already-keychain-protected storage (add a field to `StoredLocalSignatureRecord`, keep it backward-compatible/optional so existing stored records don't fail validation), so decryption is only ever possible from the same protected local store as the rest of the signature evidence. Update `signatureOutputFileNames` if the on-disk filenames need to reflect that they're now ciphertext (e.g. keep the same names — the content being opaque doesn't require renaming, your call, document it). Add a test proving: the bytes written to the fake `WorkspaceService` are not the plaintext PDF/certificate bytes (assert they're different), and that re-loading + decrypting with the key from the stored record recovers the exact original bytes (round-trip proof).
