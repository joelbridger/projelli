### 2. Real-hardware edge cases

**Sleep/resume mid-recording — genuinely can't happen by design (good), only partially testable remotely.** `powercfg /a` confirms the Legion supports Modern Standby (`S0 Low Power Idle`, network-connected) — the one sleep state remote SSH testing can plausibly reach. But `powercfg /requests` while a recording was live showed **`lantern.exe` itself holding both a `SYSTEM` and an `AWAYMODE` sleep-prevention request** (plus the USB Audio Device driver's own `SYSTEM` request for "an audio stream is currently in use"). `AWAYMODE` is the specific Windows API media/recording apps use so the system won't sleep even on lid-close while capturing — this is deliberate protection, and it means an advisor closing their laptop lid mid-recording should NOT interrupt the recording. Attempts to force `SetSuspendState` anyway (both directly and via an interactive-session scheduled task, to rule out a Session-0/SSH context issue) produced no observable sleep in the Windows Power-Troubleshooter event log — consistent with, not contradicting, the app's own request actively blocking it. **Genuinely not testable remotely without physical lid access** (same honest limitation prior cloud-bench sessions hit with firmware sleep-state support, just a different cause here).

**But: the sleep-prevention lock LEAKS — confirmed real bug, filed as QA-69.** After stopping the recording and letting transcript+notes fully complete (client fully idle, "Needs review" badge shown, nothing pending), `powercfg /requests` STILL showed `lantern.exe` holding both `SYSTEM` and `AWAYMODE` — unchanged 15+ seconds after full completion. Code review of `CpalSource::stop()` (`src-tauri/src/commands/capture/sources.rs`) shows the app's own Rust correctly signals the capture thread to stop and `.join()`s it (which does `drop(stream)`) before `stop()` returns — so this isn't the app forgetting to close its own stream. The leak is almost certainly in the `cpal` crate's WASAPI backend (confirmed as a direct dependency via `Cargo.lock`) not clearing its `SetThreadExecutionState` flags on stream `Drop`, or clearing them on a thread other than the one that set them (a documented gotcha of that Win32 API — it's process-wide, not literally per-thread, and only an explicit `SetThreadExecutionState(ES_CONTINUOUS)` call clears it). **Real user impact: once an advisor records a single meeting, their laptop can never automatically sleep again for the rest of that app session — a real, measurable battery-life regression for a desktop app advisors would keep open all day.**

**Unplug headset mid-record — not testable remotely (driver refuses removal while streaming, no physical access).** Tried `Disable-PnpDevice` and `pnputil /disable-device` against both the audio-function device and its USB-composite parent (`AB13X USB Audio`, confirmed as the actual capture device via the same `powercfg /requests` "audio stream in use" evidence). Both failed with a generic driver-level rejection (`HRESULT 0x80041001`) — my SSH session is genuinely elevated (High Mandatory Level confirmed), so this isn't a permissions issue; it reads as the driver refusing PnP removal while a WASAPI stream holds it open. A true physical unplug isn't reachable over SSH. Honestly flagging as untested rather than claiming a pass.

**Kill app mid-transcription — reproduced a real, confirmed P1, filed as QA-70.** Recorded ~25s for a fresh client (Pruitt, Jeffrey & Kimberly), clicked Stop, then immediately `Stop-Process -Force`'d `lantern.exe` before transcription could finish (confirmed via the on-disk `.transcribe-progress.json` showing only the mic channel's first chunk done, sys channel never started). Restarted the app cleanly. Result:
- **No data loss** — `audio.wav`, `meeting.json`, and the consent ledger all survived intact.
- **But the meeting is now stuck in "Transcription is queued. It'll appear here once it's ready." forever.** 35+ seconds after restart, and again after fully navigating away and back into the meeting, the on-disk progress file is byte-for-byte unchanged from before the kill — no retry was ever attempted.
- **Root-caused precisely:** the existing QA-40 "Retry" button (`retryMeetingTranscript` in `meetingStore.ts`) only appears once `transcriptError` is set on `meeting.json` — and that field is only ever written from a `catch` block around the transcription call. Killing the whole process mid-flight means that `catch` never runs, so `transcriptError` is never set (confirmed: `meeting.json` has no such field after the kill), so the Retry button never renders. There is no separate app-startup reconciliation pass that scans for meetings with audio but no transcript/error and resumes or offers to retry them. The Rust side genuinely CAN resume (`.transcribe-progress.json` is designed for exactly this), the JS side just never calls it again after an ungraceful process death.
- **Compounding risk, filed as QA-71:** the meeting's "Delete audio · keep transcript" button reads *"The audio file is deleted from this computer. The transcript and notes stay."* — but for this specific stuck meeting there is no transcript and no notes at all. Clicking it would silently and permanently destroy the ONLY copy of this meeting's content, with a confirmation dialog actively (if unintentionally) implying something will be preserved that won't be. I opened the confirmation dialog to verify this exact wording, then clicked **Cancel** rather than actually delete, to preserve the stuck meeting as live evidence. Screenshots `06`, `07`, `08`.
