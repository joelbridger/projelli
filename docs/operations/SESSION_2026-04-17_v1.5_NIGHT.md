## The RC iteration story

v1.5 required **8 release-candidate iterations** to produce a clean artifact set. Every failure was a distinct, genuine issue, not flakiness. Each was a layer of the onion that v1.0.8's CI never had to peel, because v1.5 added substantial new infrastructure (LanceDB RAG, fastembed ONNX, MCP binary, .mcpb bundling, voice sidecar plumbing).

| RC | Runtime | Failure layer | Fix |
|---|---|---|---|
| rc.1 | cancelled mid-run | `protoc` missing on CI runners, `lance-encoding`'s build.rs (via `prost-build`) needs protoc. Host dev server had it via `apt`, CI runners didn't. | Add `arduino/setup-protoc@v3` step on both jobs, pinned to protoc 25.x |
| rc.2 | ~10 min, fail | Tauri npm↔Rust minor mismatch: `@tauri-apps/plugin-updater@2.10.1` vs Rust `tauri-plugin-updater@2.9.0` | *(Attempted fix: bump Rust side, caused next failure)* |
| rc.3 | ~40 min, fail | Bumping `tauri-plugin-updater` to 2.10.1 cascaded `tauri` core from 2.9.5 → 2.10.3, which then mismatched npm `@tauri-apps/api@2.9.1` | Revert the Rust bump; pin npm `@tauri-apps/plugin-updater` back to `~2.9.0`. Align everything at 2.9.x. |
| rc.4 | cancelled mid-run | `failed to find main binary, make sure you have a package > default-run in the Cargo.toml`. Crate has 2 bins (`projelli` + `projelli-mcp`) after Phase 2, Tauri bundler couldn't pick. | Add `default-run = "projelli"` in `[package]` |
| rc.5 | ~40 min, fail | Tauri bundler tried to copy `target/release/mcp`, derived the bin name `mcp` from the directory `src/bin/mcp/`, bypassing Cargo's explicit `[[bin]] name = "projelli-mcp"` | Move MCP source from `src-tauri/src/bin/mcp/` to `src-tauri/src/mcp_bin/`, outside Cargo's auto-discovery convention |
| rc.6 | ~51 min, partial | 3/4 jobs succeeded and produced 12 signed artifacts, but `.mcpb` upload failed on every platform. Root cause: `Build .mcpb bundle` wrote to `dist/`, then `npm run tauri build`'s `beforeBuildCommand` (Vite) wiped `dist/` and replaced it with frontend assets | Change output to `mcpb-dist/`, outside Vite's output dir |
| rc.7 | ~50 min, partial | 3/4 green on full pipeline including 3 `.mcpb` bundles (Linux + Mac Intel + Mac ARM). Windows `.mcpb` upload still failed. | Fixed in rc.8 |
| rc.8 | **~38 min, GREEN ✅** | `scripts/build-mcpb.mjs` entry-point guard used `import.meta.url === \`file://${process.argv[1]}\``, works on Unix (forward-slash absolute path), fails on Windows (backslashes + drive letter). `main()` never ran, script exited 0 without writing, upload step couldn't find the file. | Replace with `fileURLToPath(import.meta.url) === process.argv[1]`, canonical Node ESM idiom. **All 4 platforms produced full artifacts including the Windows .mcpb.** |

**Why so many iterations?** Phase 2's Rust foundation was verified locally where the dev host already had protoc, matured Cargo.lock, etc. The GitHub Actions release pipeline hadn't been exercised since v1.0.8 on 2026-04-16. Every v1.5-era dep added to `Cargo.toml`, every bin added to the crate, every new build step, all needed CI validation that only happened tonight. Each failure revealed the next hidden assumption.

Final state pending CI confirmation: see "What landed on `release/v1.5`" below.

## Ship procedure (when you're ready)

**Absolute prerequisite:** dogfood checklist above is green OR you've triaged the gaps.

### 1. Tag v1.5 final

```bash
cd /home/jameson/projelli
git checkout release/v1.5
git pull origin release/v1.5
git tag v1.5
git push origin v1.5
```

This triggers the same CI workflow. Expected output: fresh signed artifacts + `latest.json`.

### 2. Manually sign Windows for auto-updater

Once CI publishes the draft release, download `Projelli_1.5.0_x64-setup.exe` from it and:

```bash
# On the server, using the Tauri updater key
cd ~/projelli
gh release download v1.5 -p "Projelli_1.5.0_x64-setup.exe" --repo projelli/projelli --dir /tmp/

# The updater key password lives in your password manager
# (search "Projelli / Tauri Updater Signing Key"), not on disk.
# Paste it when prompted:
read -s -p "Updater key password: " UPDATER_PWD
npm run tauri -- signer sign \
  -f ~/.projelli-secrets/updater.key \
  -p "$UPDATER_PWD" \
  /tmp/Projelli_1.5.0_x64-setup.exe
unset UPDATER_PWD
```

This produces `/tmp/Projelli_1.5.0_x64-setup.exe.sig`. Upload it to the release:

```bash
gh release upload v1.5 /tmp/Projelli_1.5.0_x64-setup.exe.sig --clobber --repo projelli/projelli
```

### 3. Patch `latest.json` to include the Windows entry

The v1.0.8 procedure handles this. See `docs/operations/SESSION_2026-04-16_v1.0.8_SHIP.md` §Attempt 4.

### 4. Publish the draft

```bash
gh release edit v1.5 --draft=false --latest --repo projelli/projelli
```

This makes v1.5 discoverable AND flips `latest.json` at `/releases/latest/download/latest.json` to v1.5. Every v1.0.8+ user's auto-updater will now offer the update within 24h.

### 5. Merge to master

```bash
git checkout master
git pull origin master
git merge --ff-only release/v1.5
git push origin master
```

### 6. Deploy website

```bash
cd /home/jameson/projelli
./infra/deploy.sh
```

Verify `https://projelli.com`, `https://projelli.com/templates/`, `https://projelli.com/vs/obsidian` all load.

**Heads-up: the Cloudflare cache purge will be skipped** because `~/.cloudflare-projelli-token` doesn't exist on this server and `PROJELLI_CF_ZONE_ID` isn't set in your shell. The script gracefully skips and prints what's missing. Two options:

- **Easy:** purge via the Cloudflare dashboard manually after the deploy (Caching → Configuration → Purge Cache → Purge Everything for projelli.com). Takes 60 seconds.
- **Permanent:** put your CF API token (per `reference_cloudflare_api.md`) into `~/.cloudflare-projelli-token` (chmod 600) and `export PROJELLI_CF_ZONE_ID=<zone-id-from-CF-dashboard>` in your shell rc. Then deploy.sh purges automatically.

Cache TTL on projelli.com is short (~30 min), so even without purge, visitors will see fresh content within half an hour.
