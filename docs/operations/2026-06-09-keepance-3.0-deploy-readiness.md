## 0. TL;DR - what shipping 3.0 actually means

Keepance 3.0 is not one artifact. It is **four shipping surfaces** that must come up in the right order:

1. **Desktop app v3.0.0** - the Tauri installers (Win/Mac/Linux) built by the existing tag-triggered CI. The single-user product is complete and green.
2. **The firm backend** (`backend/`) - a NEW cloud service for firm-tier identity/auth, per-org seat licensing, the E2EE sync relay, and the assured zero-retention proxy. Built + tested locally, **never deployed**. The desktop app's firm features are stubs until this is up.
3. **The website** - the 3.0 positioning + pricing page (`website/3.0/pricing.html`) is staged in the repo, NOT live. Cutover depends on Jameson ratifying positioning + pricing.
4. **Pricing/commerce** - three NEW subscription products in LemonSqueezy. Must exist before paid 3.0 sign-ups. The existing v2.5 products and live buy buttons stay untouched (grandfather).

**The honest split:** the **solo/single-user product can ship on its own** (surfaces 1, 3, 4 for the Solo/Professional tiers) without the firm backend, because solo mode is accountless, local-first, BYOK and never talks to a server. **The Firm tier cannot ship until surface 2 is deployed.** This lets Jameson stage the launch: solo first, firm when the infra is up.

## 1. The desktop app (v3.0.0)

### 1.1 Version bump plan (2.5.2 → 3.0.0)

Three files carry the version and **must move together** (a mismatch is exactly the class of bug that shipped as v2.5.0/2.5.1 failures, per CHANGELOG). Do NOT do this until go-live is gated and approved.

| File | Field | Current | Target |
|---|---|---|---|
| `package.json` | `"version"` | `2.5.2` | `3.0.0` |
| `src-tauri/tauri.conf.json` | `"version"` | `2.5.2` | `3.0.0` |
| `src-tauri/Cargo.toml` | `[package] version` | `2.5.2` | `3.0.0` |

After editing `Cargo.toml`, run `cargo build --manifest-path src-tauri/Cargo.toml` once so `Cargo.lock` updates the `keepance` package version (the 2.5.2 release explicitly called out a stale lockfile version as a fix - keep the lock in sync).

> The workspace member crate `keepance-docx` is at its own `0.1.0` and is **not** user-facing; it does **not** need to track the app version. Leave it at `0.1.0` (or bump independently if desired - it has no release meaning).

The displayed app version comes from `package.json`/`tauri.conf.json`; the auto-updater compares the tag's `latest.json` version against the installed `tauri.conf.json` version, so all three aligning is what makes the update offer correct.

### 1.2 The release tag (what triggers CI)

The release pipeline (`.github/workflows/release.yml`) triggers on **`push` of a tag matching `v*`**. So the go-live action for the desktop app is:

- **Staging / internal test:** `git tag v3.0.0-rc.1 && git push --tags` → produces signed installers for all platforms as a **draft** release, for internal testing. **RECOMMENDED - do this first. Do NOT execute it as part of this plan.**
- **Production:** `git tag v3.0.0 && git push --tags` → same pipeline, the real release.

The matrix marks `releaseDraft: true`, so even the production tag lands as a **draft** GitHub release that Jameson (or the operator) edits with the changelog and clicks **Publish**. Publishing is what flips `releases/latest` and makes the auto-updater serve it. So there is a built-in human gate between "CI built it" and "users get it."

### 1.3 CI pipeline review - does the matrix cover the NEW Rust workspace crate + the new commands?

**Yes, with no workflow change required.** Reasoning, verified against `release.yml` + `Cargo.toml`:

- The new engine crate `crates/keepance-docx` is a **workspace member** depended on by the host crate via a path dep (`keepance-docx = { path = "crates/keepance-docx" }`). Every `cargo build` / `tauri build` of the host crate compiles it transitively. The CI's `npm run tauri build` (Windows) and `tauri-apps/tauri-action` (Mac/Linux) build the host crate, so `keepance-docx` is built and bundled on every platform automatically. No new matrix entry, no separate build step.
- The new Tauri **commands** (`docx_*`, the matter/RAG/audit/privilege commands, etc.) live in the host crate (`src-tauri/src/commands/`, `src/lib.rs`) - also compiled by the same host build. Nothing new to wire.
- **`keepance-docx` only pulls generic crates** (`zip`, `quick-xml`, `serde`, `chrono`, `thiserror`) - no proprietary SDK, no protoc, no system libs. It adds no new CI dependency. (`protoc` is already installed in CI for the unrelated `lance-encoding` dep.)
- The `keepance-mcp` sidecar build, Piper TTS sidecar staging, `.mcpb` bundling, macOS nested-binary signing, and the Windows Azure-signing + updater-resign + `latest.json` merge are all **unchanged** and already proven on v2.5.2.
- **Local build passes** (per STATUS): `cargo build --bin keepance` succeeds, `npm run build` succeeds, ~50 engine Rust tests + ~299 host lib tests + 2422 frontend tests green, `tsc` clean. So the only CI-specific risks are environmental (runner images), not 3.0-code risks.

**One thing to confirm before the first 3.0 tag (CI-environment, not code):**
- The Windows job depends on the Azure Trusted Signing service principal + cert profile and on the PSGallery/NuGet bootstrap step (added in 2.5.2 to fix a runner-image regression). v2.4.1 signed fine; v2.5.0 failed on exactly this and was fixed for 2.5.2. **Run the `v3.0.0-rc.1` staging tag specifically to re-prove the Windows signing path** before the real tag - it is historically the flakiest step and the only one with a per-image dependency.
- Confirm the Azure subscription billing is active (v2.1.0 once shipped with no Windows installer because the Azure free trial had expired). A `rc.1` build surfaces this immediately.

### 1.4 Code signing + notarization + auto-updater (`latest.json` flow)

No changes needed for 3.0; this is the same machinery that shipped 2.5.2. Documented here so the operator understands the gates:

- **macOS:** `tauri-action` signs with the Developer ID Application cert (`APPLE_*` secrets) and notarizes via Apple (`APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID`). The MCP + Piper nested binaries are explicitly re-signed before bundling (Apple rejects unsigned nested binaries). If Apple notarization stalls again (it did in spring 2026), the fallback is signed-but-unnotarized (Gatekeeper "Open Anyway") - comment out the three notarization env lines, per the workflow's own note.
- **Windows:** built unsigned, then signed by Microsoft's `azure/trusted-signing-action`, then the **updater `.sig` is regenerated over the Azure-signed installer** (because Azure rewrites the bytes after Tauri's first signature). This is the subtle bit that makes Windows auto-update work - leave it intact.
- **Auto-updater:** `tauri.conf.json` has `createUpdaterArtifacts: true`, the minisign **pubkey** embedded, and the endpoint `https://github.com/keepance/keepance/releases/latest/download/latest.json`. The signing **private** key is in `TAURI_SIGNING_PRIVATE_KEY` (+ password). The `finalize-updater-manifest` job merges the `windows-x86_64` entry into `latest.json` after both build jobs finish. **The updater reads `latest/download/latest.json`, so the auto-update offer goes out only when the draft release is PUBLISHED** (publishing sets `latest`). This is the safety property that lets a 3.0 draft sit un-shipped while v2.5.2 stays live.

> **Updater compatibility note (important for a major-version bump):** existing v2.5.2 users will be offered 3.0.0 by the normal updater flow once the release is published. 3.0 introduces a license model change (all tiers become subscriptions) and the firm backend. Confirm the in-app `useLicense` degrade-gracefully behavior (see §6 NEEDS-JAMESON / engineering tail) is in the 3.0 build so an updated existing customer is never hard-locked. Existing **paid v2.5 license keys are grandfathered** (validator keeps honoring them) - see §2.4 and the LemonSqueezy setup doc's grandfather section.

### 1.5 Staging step (RECOMMENDED - do NOT execute now)

Tag `v3.0.0-rc.1` and push it to produce real signed installers as a **draft pre-release**, for internal testing on a clean Windows machine + a Mac + Linux. This:
1. Re-proves the full CI path (especially Windows Azure signing) on the actual 3.0 tree.
2. Lets Jameson install and sanity-check the major version end to end (open a .docx, run an AI redline, scope a matter, see the egress indicator) before any user is offered it.
3. Produces a `latest.json` you can inspect WITHOUT publishing (a draft pre-release does not become `releases/latest`, so no existing user is auto-offered an RC).

Recommendation: **always run at least one `-rc.N` before the production `v3.0.0` tag.** This is the single cheapest way to de-risk a major release whose only real CI unknowns are environmental.

## 2. The firm backend (`backend/`)

The firm backend is the gate for the **Firm tier** (shared matters, multi-seat sync, admin console with SSO + ethical walls, the Assured zero-retention option). Solo + Professional do **not** need it. It is built + tested locally (`bun test`: 52 tests across crypto/auth/licensing/HTTP lifecycle; `tsc --noEmit` clean) and **binds `127.0.0.1` by default** - it is explicitly **not deployed**.

### 2.1 Where it should run (recommendation)

**RECOMMENDED: home server behind the existing Cloudflare tunnel, as a hardened Bun systemd service - exactly like the existing `license-validator`.** Rationale:

- It is the **same stack and same trust model** as the live `license-validator` (`~/services/license-validator`): Bun + `Bun.serve`, binds `127.0.0.1`, Caddy terminates TLS and is the only thing that talks to it, a peer-IP loopback allowlist, and systemd hardening (`ProtectSystem=strict`, `ProtectHome=read-only`, `PrivateTmp`, `NoNewPrivileges`). Reusing that pattern is the least-surprise, lowest-ceremony path and matches every other `~/services/*`.
- Caddy already listens on `:8080` and routes per-host; adding a new firm-API host is a 4-line block. The Cloudflare tunnel already fronts `keepance.com` + `licenses.keepance.com`; adding one more hostname is a one-line tunnel ingress entry.
- The firm backend's own README says "ship this on Postgres" and "rate-limit → Redis" for production scale, but **for the launch cohort (the first ~10 firms) the home-server + SQLite path is adequate** and reversible - you can lift-and-shift to a VPS later without changing the app, because all DB access funnels through the typed `Store` class.

**Alternative (defer unless a firm deal demands it): a small managed VPS** (e.g. Fly.io / a $5–10 box) with managed Postgres + Redis. Choose this only when (a) firm volume or an SLA justifies it, or (b) a firm's security review wants the licensing/sync infra off a residential IP. The migration is mechanical (see §2.2). **Do not over-build this for launch** - start on the home server, move when a real customer requires it.

> Decision for Jameson: **home server + Cloudflare tunnel for launch** (cheapest, matches existing services, reversible). Revisit to a VPS only on a firm requirement. This is a board-adjacent infra call - flagged in §6.

### 2.2 SQLite → Postgres migration for production

Per `backend/README.md`, this is **deliberately mechanical** and only needed at firm scale:
- All DB access goes through the typed `Store` class in `backend/src/lib/db.ts`. The SQL is vanilla.
- The port swaps the driver (`bun:sqlite` → a Postgres client) and upgrades the two concurrency-sensitive transactions - `activateSeat` and `transferSeat` - from SQLite's `IMMEDIATE` transaction to Postgres `SELECT ... FOR UPDATE` / `SERIALIZABLE`, preserving the "two concurrent activations can't both slip past `seat_limit`" guarantee (which is the whole point of the seat-limit enforcement).
- **For the launch cohort, stay on SQLite** (WAL mode, the `IMMEDIATE`-transaction seat check). The README's Postgres note is a scale step, not a launch blocker. Mark it as a fast-follow.

### 2.3 Secrets management

All required in production (the server auto-generates ephemeral secrets in dev and **warns**; ephemeral secrets are unacceptable in prod because tokens don't survive a restart). From `backend/.env.example`:

| Secret | Purpose | How to generate | Notes |
|---|---|---|---|
| `AUTH_SECRET` | signs short-lived access JWTs (HS256) + HMACs refresh tokens at rest | `openssl rand -hex 48` | **must be ≥32 chars or the server throws.** Stable across restarts. |
| `SEAT_PRIVATE_KEY_PEM` / `SEAT_PUBLIC_KEY_PEM` | Ed25519 keypair that signs/verifies **seat tokens** (client embeds only the public key, verifies offline, can never mint) | `bun run keygen` (prints both PEMs + escaped env lines) | Or use `SEAT_PRIVATE_KEY_PATH`/`SEAT_PUBLIC_KEY_PATH` to point at PEM files on disk (takes precedence). **The desktop app must ship the matching PUBLIC key** (from `/.well-known/seat-pubkey`) - see §5 ordering. |
| `MANAGED_KEY_SECRET` | master secret under which org-level **managed provider API keys** are encrypted at rest (AES-256-GCM via HKDF) for the assured proxy | `openssl rand -hex 48` | Set a **dedicated** value (not derived from `AUTH_SECRET`) so it can be rotated independently. Only needed if any firm uses the Assured tier. |

Storage pattern: same as `license-validator` - an `EnvironmentFile=` (e.g. `/etc/keepance-firm-backend.env`, `chmod 600`, owned by `jameson`, **outside the repo**, never committed). The repo only ever commits `.env.example` (`.env` is gitignored). The seat private key lives in env, never the DB or repo.

> **Provider keys clarification:** there are **no global provider keys** to manage. BYOK is the default and keys never touch any server. The *only* server-side provider keys are the **per-org managed keys** for firms on the Assured tier, set by a firm admin via `POST /assured/keys/set`, encrypted at rest under `MANAGED_KEY_SECRET`, never returned, never logged. Nothing for Jameson to provision globally.

### 2.4 TLS / DNS + the `licenses.keepance.com` reconciliation (coexistence → cutover)

**Current live state (verified):**
- `licenses.keepance.com` (and legacy `licenses.projelli.com`) → Cloudflare tunnel → Caddy (`:8080`) → `127.0.0.1:5181` → the existing **`license-validator`** systemd service (`~/services/license-validator/server.ts`). It already:
  - validates LemonSqueezy license keys and issues Ed25519-signed JWTs,
  - handles the **subscription lifecycle webhooks** (`subscription_cancelled`/`_expired`/`_paused`/`order_refunded` → revoke; `subscription_payment_success`/`_resumed` → reactivate - see `tiers.ts`),
  - maps products to `personal`/`professional`/`practice` and handles legacy products,
  - is loopback-only + systemd-hardened.
- The **new firm `backend/`** is a separate, more capable service (org-scoped seats, identity/auth, sync relay, assured proxy) on port **5190**, with **no LemonSqueezy webhook ingester** (provisioning is via `POST /admin/org`, loopback-protected) and **not routed anywhere yet**.

**These two are different services with overlapping concerns. The plan is COEXISTENCE first, then a narrow cutover - not a rename or a replacement.**

**Recommended DNS layout:**
- Keep **`licenses.keepance.com` → the existing `license-validator` (5181), unchanged.** It serves every existing v2.5 buyer (grandfathered) and the per-machine validation the current desktop app already does. Do not touch it during the solo-3.0 launch.
- Stand up the firm backend on a **new, distinct host: `api.keepance.com`** (NOT `licenses.keepance.com`). This avoids any ambiguity between "validate my per-machine key" (the old validator) and "firm identity + per-org seats + sync + assured inference" (the new backend). Add:
  - one Cloudflare tunnel ingress line: `hostname: api.keepance.com` → the tunnel,
  - one Caddy host block: `@firmapi host api.keepance.com { reverse_proxy 127.0.0.1:5190 }`,
  - a Cloudflare DNS record for `api.keepance.com` (proxied).
- The desktop app's `tauri.conf.json` CSP `connect-src` currently allows `https://keepance.com` and `https://licenses.keepance.com`. **Add `https://api.keepance.com`** to `connect-src` in the 3.0 build so the firm client can reach the new backend (this is a one-line `tauri.conf.json` change that belongs with the version bump, gated to go-live).

**Subscription-lifecycle reconciliation (the one real overlap to decide):** all three 3.0 tiers are subscriptions. There are two clean options; **pick (A)** for launch:

- **(A) RECOMMENDED - the existing `license-validator` (5181) keeps owning Solo + Professional subscriptions.** It already speaks the LemonSqueezy subscription webhooks and the `personal`/`professional` codes; the 3.0 work needed there (map the new variants → tier codes + seats, issue time-limited licenses, renew/revoke on lifecycle events) is the "engineering tail" listed in the LemonSqueezy setup doc, and it is an **extension of a service that already does 90% of this**. The firm `backend/` (5190) owns only the **Firm** tier's org/seat provisioning, driven by `POST /admin/org`. The LemonSqueezy Firm-product webhook drives org creation: this needs a thin webhook → `/admin/org` bridge (the firm backend deliberately has no LS webhook of its own; the README names `/admin/org` as the one endpoint a deployment must protect at the network layer, "driven by the LemonSqueezy billing webhook behind a loopback-only reverse proxy"). The cleanest implementation is to let the existing `license-validator` (which already verifies LS webhook signatures) classify Firm orders and call `/admin/org` on the firm backend over loopback.

- **(B) Defer/avoid for launch - collapse everything into the firm backend.** Pointing `licenses.keepance.com` at the new backend and retiring the old validator is more work, risks the grandfathered v2.5 buyers, and is unnecessary for the Solo/Professional launch. Only consider this long-term, as a consolidation, well after firm volume justifies it - and only with a careful migration of the existing activation/revocation JSONL state.

**Cutover sequencing (narrow + reversible):**
1. Solo + Professional 3.0 ride the **existing** `licenses.keepance.com` validator (option A) - extend it for the new subscription variants; no DNS change.
2. Firm 3.0 rides the **new** `api.keepance.com` firm backend - additive DNS/Caddy/tunnel, no impact on existing routing.
3. The old v2.5 LemonSqueezy products + the old validator behavior stay live the whole time (grandfather). Nothing is torn down.

### 2.5 Rate-limit → Redis

The firm backend ships an **in-memory** fixed-window rate limiter (`backend/src/lib/http.ts`): auth endpoints default 10/min, the assured proxy 120/min. For a single home-server instance this is fine. For multi-instance scale, the README's guidance is to move it to **Redis or the reverse proxy**. **For launch (single instance), keep the in-memory limiter.** Mark Redis as a fast-follow tied to the same trigger as the Postgres migration (multi-instance / VPS).

### 2.6 Order relative to the desktop app

**The firm backend must be up BEFORE the desktop app's firm features are usable** (firm sign-in → `/org/activate` → seat token; sync relay; assured proxy all require it). But because solo mode never talks to a server, **the solo/single-user 3.0 app can ship first**, with firm features inert/stubbed, and the firm backend can come up after. See the sequenced checklist in §5.

### Phase A - desktop staging build (gate: G0)

## 6. Rollback plan

The architecture makes 3.0 **fail-safe by default**: v2.5.2 stays the live, shipping product until each surface is deliberately cut over, and the auto-update offer only goes out when the GitHub release is **published**.

- **Desktop app:** If the production `v3.0.0` release is bad, **do not publish the draft** (the cleanest "rollback" is never flipping `latest`). If already published: re-point users back by publishing a higher-versioned re-release of the known-good build, or unpublish 3.0.0 so `releases/latest` falls back to v2.5.2 (the updater reads `latest/download/latest.json`). Because the bump is a normal tag, you can also tag `v3.0.1` off a revert. **Installed v2.5.2 clients keep working regardless** - they only update when offered a published newer release. (Note: a user who already updated to 3.0.0 won't be auto-downgraded; standard Tauri-updater semantics.)
- **Website:** `deploy.sh` is `rsync --delete` from `website/` → the web root. To roll back, restore `website/` to the pre-cutover state on `keepance-3.0`/`main` and re-run `deploy.sh` (+ CF purge). Keep the v2.5 `website/index.html` content in git history so the previous live page is one revert away. The staged 3.0 page is `noindex` until promoted, so a botched promotion is contained.
- **LemonSqueezy:** the 3.0 products are NEW and additive; rolling back commerce = unpublish the three 3.0 products (existing licenses keep validating - validation is independent of whether a product is purchasable). The v2.5 products were never touched.
- **Firm backend:** additive - it only affects `api.keepance.com` (new) and the Firm tier. Rolling it back = stop the systemd service + remove the `api.keepance.com` tunnel/Caddy entry. **`licenses.keepance.com` (5181) is never modified during firm rollout, so solo/v2.5 licensing is unaffected.** The firm DB is SQLite at a known path; back it up before any change (B2 backups already cover `~/services` patterns).
- **Version files:** the 2.5.2 → 3.0.0 bump lives on a release-prep commit on `keepance-3.0`; reverting it restores the version state. Keep `Cargo.lock` in the same commit so a revert is clean.

## 8. Risks / call-outs

- **Windows Azure signing is the historical flake** (failed on v2.5.0, fixed for 2.5.2 with the PSGallery/NuGet bootstrap; v2.1.0 once shipped with NO Windows installer because the Azure trial lapsed). The `v3.0.0-rc.1` staging tag exists to surface this BEFORE the real tag. Confirm Azure billing is active.
- **Version-string drift breaks installers silently** - the 2.5.0/2.5.1 builds never completed; a stale `Cargo.toml` version was a named fix. Bump all three files together and sync `Cargo.lock`; let `tsc --noEmit` gate (vitest does not type-check).
- **Two licensing services with overlapping concerns.** `licenses.keepance.com` (5181, existing validator) vs the new firm `backend/` (5190). The plan keeps them **separate** (validator owns Solo/Pro subscriptions; firm backend owns Firm orgs on `api.keepance.com`) to avoid risking grandfathered buyers. Collapsing them is explicitly deferred.
- **Major-version auto-update of existing users.** Publishing 3.0.0 offers it to every v2.5.2 user. Confirm the lapsed-subscription degrade-gracefully behavior is in the 3.0 build so an updated user is never hard-locked, and that grandfathered keys still validate, BEFORE publishing.
- **The firm half is not a click.** The firm-client desktop wiring (seat tokens in the keychain, sync-relay client, per-matter key release/rotation incl. admin escrow, assured-proxy client) is real engineering that is **not yet built** (`backend/README.md` "what the desktop wiring needs"). The Firm tier cannot go live until it is. The solo launch does not depend on it.
- **`deploy.sh` is immediate + `rsync --delete`.** It rebuilds and re-syncs the `/try/` web demo too. Verify the live page body after deploy (Caddy catch-all can return 200 on a wrong path).
- **Provider-side ZDR caveat for the Assured tier.** The assured proxy guarantees *Keepance* retains nothing, but the upstream provider still receives the prompt in plaintext; end-to-end zero retention requires provider-side ZDR/no-training on the managed account + the DPA. Say so to any firm that asks. BYOK-direct remains the strongest story and the default.
