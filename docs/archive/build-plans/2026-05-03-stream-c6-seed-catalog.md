# Projelli v2.0 Stream C6: Seed Catalog + Submission Process

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up the two community-content GitHub repos (`projelli/community-templates`, `projelli/community-plugins`), seed each with day-one content (5-10 curated templates beyond the 12 built-ins for templates; the 4 example plugins from C5 for plugins), wire a GitHub Action on each repo that rebuilds `catalog.json` on PR merge, document the submission process in the website docs and the repo READMEs, and verify end-to-end that the C1 + C4 marketplace UIs can fetch + install entries from the live repos.

**Branch:** `feature/stream-c6-seed-catalog`. Branches off `master` (after #21 templates marketplace AND C3 plugin runner AND C4 marketplace UI AND C5 dev experience all merge). C6 is the final C-stream PR; after it merges, Stream C is done.

**Why C6 last:** C6 needs the example plugins from C5 as catalog content, needs the marketplace UIs from C1 + C4 to test the live install path, and the GitHub Action that rebuilds `catalog.json` should know the validated manifest schemas from C1 (templates) + C3 (plugins). Order matters.

**Architecture:**

- **Two GitHub repos under the projelli org:**
  - `projelli/community-templates`: holds template entries + `catalog.json`
  - `projelli/community-plugins`: holds plugin entries + `catalog.json`
- **Repo layout (mirrored across both):**
  ```
  /
  ├── README.md              (submission instructions)
  ├── catalog.json           (auto-generated by Action; never hand-edited)
  ├── entries/
  │   └── <id>/
  │       ├── manifest.json
  │       ├── <files...>     (template.md, workflow.json, OR plugin index.js)
  │       ├── tarball.tar.gz (auto-generated by Action; never hand-committed)
  │       └── screenshots/
  ├── .github/
  │   └── workflows/
  │       └── build-catalog.yml  (rebuilds catalog.json + per-entry tarballs on PR merge)
  └── scripts/
      └── build-catalog.mjs   (the Action's logic, also runnable locally for dev)
  ```
- **GitHub Action**: on PR merge to `main`, runs `node scripts/build-catalog.mjs` which (1) walks `entries/`, (2) validates each manifest with the Zod schema (vendored from the projelli app's source), (3) tars each entry directory excluding `tarball.tar.gz` itself, (4) computes SHA-256 of the tarball, (5) generates `catalog.json` with all entries' metadata + tarball URL + checksum, (6) commits the regenerated `catalog.json` + tarballs back to `main`.
- **Submission flow**: author forks repo, adds `entries/<id>/` with manifest + files + screenshots, opens PR. Claude as TL reviews schema validity + obvious quality. Jameson reviews positioning fit. Merge triggers Action → catalog refresh → user sees new entry on next `MarketplaceService.refresh()` (24h cache TTL or manual refresh).

**Tech Stack:** GitHub Actions, Node 22, TypeScript (Zod schema vendored from app source), `tar` package for tarball creation. No Projelli app code changes (or minimal: the projelli app's website docs + perhaps a one-line marketplace help link).

**Spec reference:** `docs/superpowers/specs/2026-04-28-v2.0-mega-release-design.md` section 6.8.

## Group I: Source-of-truth Action workflow + script

- [ ] **Task 1.1** — `infra/community-repos/build-catalog.mjs`. Node 22 ESM script. Walks `entries/<id>/` dirs. For each: reads `manifest.json`, validates with vendored Zod schema (vendored from `~/projelli/src/modules/marketplace/manifestValidator.ts` for templates, `~/projelli/src/modules/plugins/PluginManifestSchema.ts` for plugins; the script knows which schema to use based on the repo it's in via an env var or filename convention).
- [ ] **Task 1.2** — Same script: tars each entry dir to `entries/<id>/tarball.tar.gz` (excluding `tarball.tar.gz` itself). Computes SHA-256 + writes alongside in `entries/<id>/checksum.txt`.
- [ ] **Task 1.3** — Same script: generates `catalog.json` at repo root with all valid entries' metadata in the `CatalogEntry` shape (id, name, description, version, author, category, tags, screenshots URLs pointing to `raw.githubusercontent.com/...`, installUrl pointing to the tarball, manifestUrl pointing to manifest.json, minProjelliVersion, optional maxProjelliVersion, publishedAt, updatedAt, checksum).
- [ ] **Task 1.4** — Same script: writes `catalog.json` and stages the changes for commit. Action commits on the source PR's merge; locally the script just writes files.
- [ ] **Task 1.5** — `infra/community-repos/build-catalog.yml`. GitHub Action workflow: triggers on push to `main`, runs `node scripts/build-catalog.mjs`, commits the regenerated `catalog.json` + tarballs back via `peter-evans/create-pull-request` or a direct commit-and-push using `GITHUB_TOKEN`.
- [ ] **Task 1.6** — Local-test the build script: in a temp dir, set up `entries/foo-template/` with a valid manifest + files, run `node build-catalog.mjs`, verify `catalog.json` is generated correctly + tarball has the right SHA.

## Acceptance criteria

- Two live GitHub repos (`projelli/community-templates`, `projelli/community-plugins`) exist with seed content.
- Each repo's `catalog.json` is auto-generated on PR merge and publicly fetchable via raw.githubusercontent.com.
- A user opening Projelli's Marketplace tab sees the seeded entries within 24h (cache TTL) of repo creation, or immediately on a manual refresh.
- A user can install at least one template + at least one plugin from the live marketplace and use them.
- The submission flow is documented in two places (the repo READMEs + projelli.com docs) and the docs are clear enough that a contributor could submit without prior context.
- Local-build script (`build-catalog.mjs`) is reproducible: running it on the same `entries/` produces an identical `catalog.json`.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Manifest schema drifts between projelli app source and the GitHub Action's vendored copy | Sync script copies the schema file from app source on every run. CI in projelli/projelli verifies the in-repo `infra/community-repos/build-catalog.mjs` references the current schema shape. |
| Bot commits trigger infinite Action loops | Action uses `[skip ci]` in its commit message OR uses `GITHUB_TOKEN` (which doesn't trigger workflows by default). |
| Tarball SHA mismatch between Action-generated and what marketplace expects | Action uses the exact same `tar` invocation we test with locally. Lock tar version in the Action workflow. |
| Empty catalog at launch (no seed) | Group III + IV deliver day-one seed of 5-10 templates + 4 plugins. Catalog is non-empty before C6 PR opens. |
| Reviewers (Claude as TL) miss malicious plugin | Manual review for v2.0 (per spec). Plugin source must be human-readable. Automated scanner deferred to v2.x. CODEOWNERS limits merge to projelli org admins. |
| Live network test is flaky in CI | Test gated behind `LIVE_NETWORK_OK` env var. CI doesn't set it. Local devs opt in. |
