## The starting state

v1.0.7 was live. Document format stubs (`.csv`, `.xlsx`, `.doc`, `.docx`, etc.) fell through to a broken PDFViewer placeholder. The welcome dialog was a dark generic Radix dialog. There was no Settings menu. There was no auto-updater — every release required users to manually re-download and re-install.

## What shipped in v1.0.8

### Headline features

- **Auto-update system** (the biggest single deliverable) — check-then-prompt flow. GitHub Releases + `latest.json` manifest + minisign signatures verified against an embedded pubkey. Settings integration.
- **Document suite** — `.xlsx` `.csv` `.docx` `.pptx` `.ppt` `.rtf` preview + edit + create with round-trip preservation. Live formula engine (in-house because HyperFormula is GPL-3). Column resize, ARIA roles, formula bar, selection summary.
- **AI ambient context** — open files auto-inject into chat. Per-tab sparkle-chip toggle.
- **AI Assistant as main-panel tab** (`Ctrl+Shift+A`) on top of the existing sidebar.
- **Workflow executions as `.workflow` files** — persistent, clickable, amber icon.
- **Schema-driven Settings modal** (`Ctrl+,` or gear icon) — 16 settings across 5 categories, Export/Import/Reset, adding new settings is a one-line schema entry.
- **Branded start screen** — white full-viewport page with coral logo + blue-purple-pink gradient glow from the website design language.
- **Keyboard shortcuts overlay** (`?` key) backed by a single source of truth at `src/utils/shortcuts.ts`.
- **`Ctrl+P` fuzzy file switcher** (fuse.js). **Full-text content search** (minisearch). **Drag-drop file upload**.
- **30+ UX polish items** across 7 waves — colored file icons, breadcrumbs, reactive save indicator, empty states, delete undo, theme system cycle, and more.

## Critical operational knowledge

### Tauri updater key — do not lose this

- **Private key file:** `~/.projelli-secrets/updater.key` on the server, chmod 600
- **Public key:** `~/.projelli-secrets/updater.key.pub`, also embedded in `src-tauri/tauri.conf.json` (`plugins.updater.pubkey`)
- **Password:** stored in Jameson's password manager under "Projelli / Tauri Updater Signing Key"
- **GitHub Secrets:** `TAURI_SIGNING_PRIVATE_KEY` + `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, both set via `gh secret set` directly from the server

**Why this matters:** The embedded pubkey in every installed copy of v1.0.8+ is the only thing those installs will verify updates against. If the matching private key is lost or leaked, EVERY installed copy of v1.0.8+ permanently loses auto-update. Users would have to manually reinstall a v1.0.8-post-rotation build to recover. Treat the key like a root CA.

**Rotation procedure** (if ever needed):
1. Generate a new keypair: `npm run tauri signer generate -- -w ~/.projelli-secrets/updater.key`
2. Update `tauri.conf.json` with new pubkey
3. Update GitHub Secrets
4. Ship a new release (existing users can't auto-update to it; they must reinstall manually)
5. Communicate to users via email / website banner

### GitHub Secrets pasting gotcha

**Never paste long base64 secrets through a chat UI.** Chat renderers insert soft-wrap whitespace that looks invisible but corrupts the value. The v1.0.8 ship hit this: the first `TAURI_SIGNING_PRIVATE_KEY` attempt had a space at offset 270, and the build failed with `failed to decode base64 secret key: Invalid symbol 32, offset 270`.

**Always use stdin transfer from an actual file:**
```bash
cat ~/.projelli-secrets/updater.key | gh secret set TAURI_SIGNING_PRIVATE_KEY --repo projelli/projelli
```

Byte-perfect. No copy-paste.

### Windows CI signing gap (UX-42)

The `build-windows` job doesn't use `tauri-action` because Azure Trusted Signing has to run as a separate step. As a result:
- No `.exe.sig` file is produced
- `latest.json` has no `windows-x86_64` entry
- Windows users can't auto-update

**For v1.0.8 this was patched manually on the server** after the CI run finished:
```bash
# 1. Download the Azure-signed .exe from the draft
cd /tmp/v108-signing
gh release download v1.0.8 --repo projelli/projelli --pattern 'Projelli_1.0.8_x64-setup.exe' --clobber

# 2. Sign it with the Tauri updater key
cd ~/projelli
npm run tauri -- signer sign \
  -f ~/.projelli-secrets/updater.key \
  -p 'Pr0j3lli-Updater-2026!' \
  /tmp/v108-signing/Projelli_1.0.8_x64-setup.exe

# 3. Upload the .sig
cd /tmp/v108-signing
gh release upload v1.0.8 Projelli_1.0.8_x64-setup.exe.sig --repo projelli/projelli --clobber

# 4. Download, patch, and re-upload latest.json
cd /tmp
gh release download v1.0.8 --repo projelli/projelli --pattern 'latest.json' --clobber
export SIG_CONTENT=$(cat /tmp/v108-signing/Projelli_1.0.8_x64-setup.exe.sig)
python3 << 'EOF'
import json, os
with open('/tmp/latest.json', 'r') as f:
    data = json.load(f)
data['platforms']['windows-x86_64'] = {
    'signature': os.environ['SIG_CONTENT'],
    'url': 'https://github.com/projelli/projelli/releases/download/v1.0.8/Projelli_1.0.8_x64-setup.exe'
}
with open('/tmp/latest.json', 'w') as f:
    json.dump(data, f, indent=2)
EOF
gh release upload v1.0.8 /tmp/latest.json --repo projelli/projelli --clobber
```

**For v1.0.9 onward** — UX-42 in the backlog describes adding a CI step that does this automatically. Effort: S. Should happen before the next release.

### Release workflow — the full sequence

Tagging `v1.0.X` triggers `.github/workflows/release.yml`:

1. `build (macos-latest, aarch64)` — Apple Silicon
2. `build (macos-latest, x86_64)` — Intel Mac
3. `build (ubuntu-22.04)` — Linux AppImage + deb + rpm
4. `build-windows` — Windows `.exe` + `.msi` (Azure-signed)
5. All 4 jobs upload to a draft GitHub release
6. `tauri-action` (the Mac/Linux jobs) generates `latest.json`

Mac/Linux gets auto-updater support out of the box. Windows needs the manual patch until UX-42 ships.

After CI, manual publishing:
```bash
gh release edit v1.0.X --repo projelli/projelli \
  --notes-file /tmp/release-notes.md \
  --draft=false --latest
```

Or edit via the GitHub web UI.

## The four botched v1.0.8 ship attempts

For future context on what can go wrong:

1. **Wrong tag position** — Tagged v1.0.8 on old master (`fbbcd88`) before the updater commits had been merged. CI succeeded but built v1.0.7-era code as v1.0.8. **Fix:** deleted draft, fast-forwarded master via `git push origin feat/document-support:master`, moved tag with `git push origin :refs/tags/v1.0.8 && git tag v1.0.8 <correct-sha> && git push origin v1.0.8`.

2. **Corrupted secret** — The `TAURI_SIGNING_PRIVATE_KEY` GitHub Secret had a whitespace character at offset 270 from chat-UI soft-wrap. Build failed. **Fix:** re-set both secrets with `cat file | gh secret set` (byte-perfect stdin transfer).

3. **Race condition in draft** — First re-run succeeded on 4 jobs but the draft only had Linux artifacts — macOS uploads race-raced away when jobs tried to write to the same draft simultaneously. **Fix:** deleted the draft entirely, did a FULL workflow re-run (not just `--failed`). Artifacts landed clean.

4. **Missing Windows in `latest.json`** — Architecture limitation documented above. **Fix:** manual patch (UX-42 will automate).

**Lesson:** before a big release, verify the tag points at the right commit (`git show v1.0.X`), verify GitHub Secrets via a dry run, and budget time for 2-3 ship attempts on the first run of a new pipeline.

## The subagent-driven wave pattern

This session heavily used a pattern worth documenting for future large refactors:

1. **Write the plan up front** — one markdown doc with the scope, organized into "waves" (coherent chunks)
2. **One subagent per wave** — dispatched in background with a detailed brief, clear acceptance criteria, explicit stop-conditions ("if any single ticket takes >45 min, commit what works and move on")
3. **Require commits as they go** — one commit per ticket, each typechecks, not batched
4. **Pull the diff to verify** — don't trust the agent's summary; read the actual changes
5. **Update the backlog doc after each wave** — change status `📋` → `✅ Done — hash: <commit>`, fill in the execution log

Main thread stays light — just briefing, verifying, and pushing. Each subagent handles its entire wave in one focused run.

Ten waves ran this way. Every one landed clean. **This is the right pattern for future 10+ ticket batches.**

Don't use it for:
- Exploratory work (main thread should explore first)
- Single-file changes (just do it)
- Tightly coupled work where each ticket depends on the previous (harder to parallelize or even serialize across agents without context leakage)
