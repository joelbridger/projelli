# Deep Research Assessment of Keepance Testing

## Executive assessment

Keepance’s current testing philosophy is directionally strong. Your attached memo shows a sensible split between a fast automated gate and a slower, higher-value real-Windows loop that drives the actual shipped-style desktop app through WebView2 on a Windows bench. That is the right instinct for a local-first Tauri application whose most important failures show up in native behaviors, file dialogs, Windows paths, indexing, and live AI flows rather than in isolated unit logic alone. fileciteturn0file0

The core problem is not that you are doing real-OS testing. The problem is that too much defect discovery still appears to be happening in the slowest and least deterministic layer. Modern testing practice is usually strongest when it pushes the maximum amount of verification down into faster, more reproducible layers, while preserving a thinner set of high-value end-to-end and exploratory checks at the top. Thoughtworks’ practical “test pyramid” framing argues for many more low-level tests than expensive UI tests, and Playwright’s own guidance emphasizes isolated, resilient tests that verify user-visible behavior without unnecessary serial coupling. Tauri itself supports both mock-runtime testing and end-to-end automation on supported desktop platforms, which means Keepance does not have to choose between speed and realism; it can do both, at different layers. citeturn12view0turn6view2turn6view4turn7view0

My overall conclusion is that Keepance should **keep** real-Windows verification as the release truth, but **shrink, harden, and parallelize** that layer. The biggest gains will come from making the Windows loop more persistent, more fixture-driven, more artifact-rich, and less dependent on full re-indexes plus live-model variability every time a branch needs proof. Buying more Windows machines can help, but it is not the first lever and it will not fully solve the present bottlenecks unless the harness changes first. fileciteturn0file0 citeturn6view0turn16view0

## Why the current loop feels slow

The attached memo identifies the bottlenecks accurately, and they explain almost all of the drag you are feeling. The biggest one is architectural: your most valuable layer is also the most serialized layer. The bench is reached over SSH, many actions are fresh round-trips, and a meaningful portion of the sweep is still one surface at a time. Playwright’s own docs are blunt that serial mode is generally not the desired steady state, and that isolated tests are preferable because they can run independently and in parallel. When the “truth” layer is mostly serial, every improvement in AI coding speed upstream can just create a wider queue downstream. fileciteturn0file0 citeturn16view0turn6view2

State reset and indexing are the second major drag source. Your memo describes a clean re-import of hundreds of files, including many PDFs and OCR content, plus a known race around storage flushing and residue. That means many test cycles begin by reconstructing the world before they can actually test the change. In effect, the system is paying a large “environment tax” before each meaningful assertion. That tax is especially painful because your real-app loop is already doing authentic OS and AI work. fileciteturn0file0

The live-model dependency is the third structural slowdown. For “Ask” and Client Map flows, your memo says outputs vary run to run and consume real tokens, with no record/replay or deterministic fixture mode. That means the loop is paying in three currencies at once: time, money, and uncertainty. Anthropic’s documentation recommends grounding long-document tasks with direct quotes and claim-level citations so outputs can be audited and unsupported claims retracted, while OpenAI’s eval guidance recommends defining representative tasks, building datasets, and grading outputs against explicit criteria. In other words, the current Keepance loop is doing some of the most expensive LLM testing possible while missing some of the main tools the LLM vendors themselves recommend for making that testing systematic. fileciteturn0file0 citeturn9view5turn9view1

The last major slowdown is observability. Your memo says screenshots are pulled back and reviewed manually, and there is no automated visual baseline for the real app. Playwright offers trace capture with screenshots, DOM snapshots, console and network inspection, and explicitly recommends recording traces on the first retry in CI; it also supports screenshot-based visual comparisons, though it warns that the baseline environment must be stable because rendering varies by OS, version, hardware, and even power conditions. Right now, Keepance is doing a lot of high-touch diagnosis that could be made faster if every failure automatically brought its own evidence bundle. fileciteturn0file0 citeturn4view0turn6view1

This also matters because flaky UI/system tests are a known tax on developer throughput. Google reported that, in their large corpus, about 1.5% of all test runs were flaky, roughly 16% of tests had some flakiness, and they ended up building rerun and quarantine mechanisms because false positives slowed real engineering work so much. Keepance is not Google, but the pattern is the same: when your slowest tests are also your least deterministic tests, velocity degrades quickly. citeturn11view0

## What best practices would change first

The single most important design change is to turn Keepance’s current test stack into a more explicit **hourglass**. At the bottom should remain the large fast gate you already have. In the middle, you should add more deterministic contract and integration coverage specifically around the Rust–Tauri boundary, retrieval isolation, indexing state transitions, workspace resets, and AI-result post-processing. At the top, you should keep a much smaller set of Windows desktop smoke flows plus a separate exploratory sweep layer for product-quality judgment. This preserves the truth of real-Windows testing without forcing every branch to rediscover every problem there. Tauri’s test model supports exactly this kind of split: mock-runtime tests for non-native paths, plus desktop automation for the real app where needed. fileciteturn0file0 citeturn6view4turn7view0turn12view0

The highest-return change after that is a **deterministic fixture mode for AI surfaces**. Keepance already has a synthetic Northcrest corpus. Use it to create canonical prompts, canonical source excerpts, and canonical expected behaviors for “Ask,” Client Map generation, citation verification, cross-client isolation, and error states. Where possible, intercept model traffic and replay recorded responses or HAR fixtures instead of hitting live providers on every verification pass. Playwright supports direct API mocking, HAR replay, and even WebSocket interception/modification, which makes it practical to create a desktop smoke suite that is deterministic even when the production app usually talks to live services. Anthropic’s recommendation to ground outputs in direct quotes and verify claims with citations is a particularly good fit for Keepance because citation trust is central to the product itself. fileciteturn0file0 citeturn15view1turn9view5turn9view1

The third change is a **persistent bench daemon**. Your memo itself proposes a persistent CDP session as an idea worth exploring, and I think that is exactly right. Today, too much work sounds like “spawn an SSH call, run one action, exit.” Replace that with a resident Windows-side service that keeps a live Playwright/CDP session, accepts queued actions, streams logs/artifacts back, and can execute higher-level verbs such as `reset_to_seed`, `open_workspace`, `build_client_map`, `ask_question`, `capture_trace`, and `export_artifact_bundle`. This is not a niche optimization. It directly attacks the round-trip latency, inline-script mangling, and command-fragmentation issues your memo calls out. fileciteturn0file0

The fourth change is to create a true **factory-reset primitive**. Do not merely clear storage and then hope the environment is clean. Instead, treat the Windows bench like an image-based test appliance. Keep a versioned, reseedable profile or workspace snapshot for the synthetic dataset, ideally including precomputed indexes when the test scenario does not specifically need to validate indexing itself. Playwright’s guidance on isolation and worker-pristine environments supports this direction, and the practical benefit is enormous: it turns “wait for a full world rebuild” into “clone a known good world.” Keep full re-import and full re-index only for the handful of tests whose purpose is to verify those features directly. fileciteturn0file0 citeturn6view2turn16view0

The fifth change is to make failures far more legible to AI agents and to you. Turn on Playwright tracing on first retry for all automated desktop flows. Persist screenshots, DOM/action snapshots, console logs, network logs, and, for AI screens, the exact cited excerpts used to ground the result. Use visual baselines only on a pinned clean verifier machine, because Playwright warns that screenshot output depends on the environment. This matters even more in Tauri/WebView2 land, where Edge/WebView2/driver versions need to remain aligned on Windows to avoid hangs and connect issues. citeturn4view0turn6view1turn7view0

One tool choice I would **not** prioritize is replacing your native dialog helper with WinAppDriver-based infrastructure. Microsoft’s WinAppDriver page still exists, and Appium’s Windows driver still proxies to it, but Appium’s own README warns that the underlying WinAppDriver server has not been maintained by Microsoft for years and suggests third-party replacements for modern use. For Keepance, that makes a wholesale migration risky. A more pragmatic path is to keep the existing native-agent approach, but wrap it in stronger, testable verbs and artifact capture. citeturn13view0turn13view1

## Whether more Windows machines will help

Yes, but not as much as it might seem if you buy them before fixing the harness.

Playwright’s sharding guidance says plainly that shardable suites can complete proportionally faster when split across multiple machines, and in the ideal case four shards on four machines can finish four times faster. But that is an idealized test-runner world. Your actual loop also includes serial reset work, indexing, rebuild/restart, branch review, merge, and human interpretation of exploratory findings. So the relevant question is not “can multiple machines speed tests up?” but “what share of the real Keepance cycle is truly distributable across benches?” citeturn6view0 fileciteturn0file0

My planning estimate is this: **one additional Windows machine is worthwhile; a third is conditional**. Based on your memo, I would model the current process as having a meaningful but not dominant parallelizable portion. Under that assumption, a second Windows machine likely improves **overall end-to-end cycle throughput by roughly 20% to 35% at first**, mostly by letting one branch verify on a clean machine while another bench is rebuilding, reindexing, or being used for exploratory work. A third machine probably adds only **another 10% to 20% overall** until you have more deterministic fixture-based suites and a proper queueable harness. Once you do have those harness improvements, I think **two machines can plausibly yield about 1.5x total testing throughput**, and **three machines can plausibly reach about 1.7x to 2.0x**, but that latter range depends on making the workload much more shardable than it is today. This is my inference from your described serial bottlenecks plus Playwright’s near-linear gains for genuinely shardable work, not a direct benchmark measurement. fileciteturn0file0 citeturn6view0turn16view0

If you add a second Windows box, the best topology is not “two identical ad hoc testing laptops,” but a **role split**. Keep one as the **fast development bench** where preview-mode iteration and rough exploratory work happen. Make the second the **clean verifier** with pinned Windows version, pinned Edge/WebView2 runtime, pinned DPI/display scaling, and the visual baseline store. That matters because Playwright warns that screenshot baselines vary by OS, version, hardware, and power source, and Tauri’s Windows WebDriver guidance warns that Edge and EdgeDriver version mismatch can cause hangs. Standardization matters more than raw machine count. citeturn6view1turn7view0

A third machine makes sense only after the automated Windows smoke pack is good enough to run unattended. At that point, I would seriously consider making the third environment a **fresh cloud Windows runner** for synthetic data only, not a permanent additional physical PC. GitHub’s hosted-runner docs say Windows runners are available as new virtual machines, and GitHub also supports customizable larger runners and concurrency controls. That gives you a clean-room Windows environment for automated smoke or nightly runs without extra hardware maintenance. Because Keepance is explicitly local-first and handles highly sensitive client material, that cloud path should be reserved for your synthetic Northcrest-style datasets and fixture traffic, not private production client data. citeturn18view1turn18view0turn12view1turn14view0 fileciteturn0file0

## Recommended operating model

The right operating model for Keepance is a **proof pipeline** that matches how Claude Code and its subagents naturally work. A subagent should not finish a task by saying “the code is changed.” It should finish by attaching evidence from progressively more expensive layers. In practice, the default flow should look like this: first, the subagent runs the fast gate and any targeted contract/component tests; second, if the change touches desktop-risky surfaces, the change triggers a deterministic Windows smoke run with fixture AI responses and a seeded workspace; third, only high-risk or user-experience-heavy changes graduate to a broader real-model exploratory sweep; and fourth, release candidates still get the full clean-slate, real-Windows, real-artifact proof pass you already value. That preserves the best part of your current philosophy while moving most routine confirmation out of the slow lane. fileciteturn0file0 citeturn6view4turn15view1turn4view0

I would also formalize a simple rule: **every serious bug found in the real-Windows sweep must be pushed downward within 24 hours** into one of three things — a deterministic contract/integration test, a deterministic fixture-backed Windows smoke case, or an explicit exploratory scenario that stays intentionally manual/agentic because it is about product judgment rather than binary correctness. This is how you stop the exploratory sweep from turning into a recurring rediscovery engine. It also matches the practical test-pyramid idea: keep the top thin and move repeatable truth downward. citeturn12view0turn6view2

A second rule should govern flakiness. Borrow from Google’s practice and track flaky tests as a first-class defect stream. If a Windows smoke test becomes noisy, do not leave it indefinitely in the critical path just because it occasionally catches something useful. Mark it, quarantine it, log it, and require a fix owner. Otherwise the team — or in your case the coding agents — will gradually stop trusting the system. citeturn11view0

A third rule should govern CI scheduling. Long Windows jobs are exactly the kind of workloads where newer commits should usually cancel obsolete in-progress runs. GitHub Actions supports concurrency groups and cancel-in-progress behavior, which is useful for keeping a Windows verifier from burning time on superseded commits while still queueing one-at-a-time release or deployment proofs when you want that behavior instead. For Keepance, that means branch smoke runs should usually be cancelable, while release-verifier jobs should usually be serialized. citeturn12view1

If I were prioritizing the next month, I would do this in order. First, build the persistent bench daemon and a true `reset_to_seed` command, because they reduce friction in every subsequent test. Second, add deterministic fixture mode for AI surfaces using your synthetic corpus, because that is where the largest combined time-and-cost waste is happening today. Third, attach trace/video/console/network artifacts to every automated Windows failure. Fourth, standardize a clean verifier machine and start visual baselines there. Only then would I buy the second Windows machine if you have not already done so; otherwise you risk scaling a slow process rather than fixing it. fileciteturn0file0 citeturn15view1turn4view0turn6view1turn6view0

The bottom line is that Keepance does **not** need less real-Windows testing. It needs **less accidental dependence** on real-Windows testing for routine confidence. The best version of this process is one where the bench is still the final judge, but not the place where every branch first learns whether it broke the product. fileciteturn0file0 citeturn12view0turn6view2
