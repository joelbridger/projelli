# Projelli v2.0 Mega-Release Design

## Executive summary

v2.0 ships all 9 product gaps identified in `docs/strategy/competitive-product-gaps-and-implementation.md` as a single coordinated release. Five deliberate non-goals from that doc (cloud sync built-in, real-time collaboration, agentic AI, mass-market subscription tier, verticalization) remain NEVER. The original phased v1.8/v1.9/v2.0/v2.1+ roadmap is collapsed into one mega-release, with all features parallelized across 5 implementation streams running concurrently in worktree-isolated subagents.

This spec documents the locked scope, locked path-level decisions per gap, locked execution model, cross-stream foundations, per-stream design, and integration plan. An agent reading this spec should be able to build from it without re-reading the brainstorming conversation.

## Decision provenance

This design was produced through a brainstorming session between Jameson Daines (founder) and Claude (CEO/TL mode) on 2026-04-28. The session proceeded through:

1. Scope confirmation (excluded 5 anti-patterns; 9 gaps in scope)
2. Path-level decisions per gap (Mobile D1+D2, Plugin GitHub-discovery, PDF hybrid, TTS Piper, Templates GitHub, i18n ES+DE, Web demo sandbox, Long context full UX)
3. Execution model selection (Approach 2: big-bang v2.0)
4. Parallelization model (4 streams + i18n final pass; worktree-isolated subagents from one Claude session)
5. Hard go/no-go spike gates (plugin sandbox, Tauri 2 mobile)
6. Section-by-section design walkthrough (foundations + 5 streams + integration plan)

Each decision was approved explicitly by Jameson before this spec was written.

## Anti-pattern follow-up

After v2.0 ships, conduct a retrospective on the 5 deliberate non-goals (cloud sync, real-time collab, agentic AI, mass-market subscription, verticalization) to determine whether buyer signal has changed any of them. This is a board-level conversation. Trigger: 30-day post-ship monitoring window completes.

## 2. Locked execution model

### 2.1 Approach selection

Approach 2: big-bang v2.0. All 9 features ship simultaneously. No mini-releases between v1.7.2 and v2.0. Marketing event is the v2.0 ship date.

### 2.2 Parallelization model

5 implementation streams run concurrently:

- Stream A: Chat Attachments + Long Context (groups 4.1, 4.2, 4.5)
- Stream B: Sidecars (4.6 TTS only for v2.0)
- Stream C: Discovery Ecosystem (4.7 plugin system + 4.9 templates marketplace)
- Stream D: New Surfaces (4.3 mobile + 4.4 web demo)
- Stream E: i18n (4.8), gates last, runs after all other streams merge

Streams A through D execute in parallel after foundations land. Stream E starts only after A, B, C, D merge to main.

### 2.3 Mechanics

Worktree-isolated subagents dispatched from one Claude Code session. Claude (TL) reviews PRs from each stream before merge. Jameson (CEO) is consulted on cross-stream decisions, scope deviations, and risk-level calls.

### 2.4 Hard go/no-go spike gates

Two spikes block the bulk of stream work and must pass before commit:

- C-spike: Plugin runner sandbox validation (web worker isolation, API proxy, permission enforcement). Pass criteria in Section 6.4. Fail outcome: pivot to iframe-sandbox OR adjust scope OR drop plugin system from v2.0.
- D-spike: Tauri 2 mobile experimental tooling validation (iOS build, file picker, markdown render). Pass criteria in Section 7.3. Fail outcome: pivot to Capacitor OR scope-cut mobile reader.

### 3.1 Chat-Attachment System (used by Stream A)

#### Type definitions

```typescript
// src/types/chat.ts
interface ChatAttachment {
  id: string;                    // SHA-256 hash of bytes (dedup key)
  type: 'image' | 'pdf';         // open enum, more types post-v2.0
  mimeType: string;
  fileName: string;
  pathInWorkspace: string;       // 'media/2026-04/chat-image-<hash>.png'
  byteSize: number;
  metadata: {
    pages?: number;
    width?: number;
    height?: number;
    extractionMode?: 'native' | 'text-extract';
  };
}

interface ChatMessage {
  // existing fields preserved
  attachments?: ChatAttachment[];
}
```

#### New module

`src/modules/attachments/AttachmentService.ts`:

- `save(bytes, fileName, mimeType): Promise<ChatAttachment>` writes to workspace with hash-based dedup
- `read(att): Promise<Uint8Array>` retrieves bytes
- `delete(att): Promise<void>` removes file (only if no other chat references it)
- `getMimeFromExtension(ext)`, `getExtensionFromMime(mime)` utilities

#### Provider interface extension

```typescript
interface Provider {
  // existing methods preserved
  formatAttachmentForRequest(att: ChatAttachment, bytes: Uint8Array): ProviderContentBlock;
  supportsAttachment(att: ChatAttachment, model: string): boolean | string;
  // returns true | false | error message string for inline display
}
```

Each provider implements its own format method per its API: Claude uses `image` or `document` content blocks, OpenAI uses `image_url`, Gemini uses `inlineData`, Ollama uses message-level `images: [base64]`.

#### Storage convention

Files saved to `<workspace>/media/YYYY-MM/<type>-<hash>.<ext>`. Same convention as existing image-paste in editor. Re-attaching same hash is dedup, no re-write.

#### UI affordances (in chat input)

- Paperclip icon next to send button. Click opens file picker, filtered by accepted MIME types per current model.
- Paste handler. Clipboard image or PDF becomes attachment.
- Drag-drop zone covers entire input area. Visible drop overlay on dragenter.
- Inline attachment tiles below input with remove (X).
- 20 MB per-file cap, matching existing markdown-editor cap.
- If selected model does not support attachment type, show inline warning with suggested model swap. Block send until user resolves.

#### Audit log additions

- `attachment_added`: path, hash, type, size
- `attachment_sent_to_provider`: path, hash, provider name, model name
- `attachment_removed`: path, hash

#### Error handling

| Failure | Behavior |
|---|---|
| File over 20 MB | Toast, reject. |
| Unsupported MIME | Toast, reject. |
| Provider rejects request | Message-level error, attachment retained for retry. |
| File missing on reload | Graceful "file missing" state in chat history, no crash. |

#### Testing

- Unit: hash dedup, provider format methods (4 providers, 3 to 5 cases each).
- Integration: paste image, send, mock API verifies request shape per provider.
- E2E (Playwright): paste image, send, reload app, chat history persists with image.

### 3.2 GitHub Discovery JSON Format (used by Stream C)

#### Two GitHub repositories under projelli org

- `projelli/community-templates` (workflow templates)
- `projelli/community-plugins` (plugins)

Each repository has `catalog.json` at root, auto-rebuilt by GitHub Action on PR merge.

#### Catalog entry shape (shared across both)

```typescript
interface CatalogEntry {
  id: string;                    // 'investor-update-v1'
  name: string;
  description: string;
  version: string;               // semver

  category: string;
  tags: string[];
  screenshots?: string[];        // raw.githubusercontent.com URLs

  manifestUrl: string;           // path to manifest.json inside repo
  minProjelliVersion: string;
  maxProjelliVersion?: string;
  ratings?: { stars: number; count: number };  // optional, future
  publishedAt: string;
  updatedAt: string;
}
```

#### MarketplaceService

```typescript
// src/modules/marketplace/MarketplaceService.ts
class MarketplaceService<TEntry extends CatalogEntry> {
  constructor(opts: {
    repoUrl: string;
    catalogPath: string;
    cachePath: string;
    installRoot: string;
  }) { /* ... */ }

  async refresh(opts?: { silent?: boolean }): Promise<void>;
  async list(): Promise<TEntry[]>;
  async getById(id: string): Promise<TEntry | null>;
  async install(id: string, opts?: { onProgress?: ProgressFn }): Promise<InstalledEntry>;
  async uninstall(id: string): Promise<void>;

  async checkForUpdates(): Promise<UpdateInfo[]>;

```

Two instances at runtime, one per repository. Cache pattern: 24-hour TTL, stored in `<workspace>/.projelli/cache/`. Manual refresh button in UI.

#### Install flow

1. User clicks Install.
2. Service downloads tarball from `installUrl`.
3. SHA-256 checksum verified against catalog entry.
4. Extracted to `<workspace>/.projelli/{templates|plugins}/<id>/`.
5. For plugins: manifest validated by sandbox runner before activation.
6. Audit log entry: `template_installed_from_marketplace` or `plugin_installed`.

#### Submission flow (out-of-band)

Authors fork repo, add their entry directory under `entries/<id>/`, submit PR. Manual approval (Claude as TL reviews, Jameson reviews positioning fit) for v2.0. Automated validation deferred. GitHub Action auto-rebuilds `catalog.json` on merge.

#### Error handling

| Failure | Behavior |
|---|---|
| Catalog fetch fails | Use cached version. Surface "marketplace offline" indicator. |
| Tarball checksum mismatch | Reject install. Audit log entry. |
| Manifest schema invalid | Reject install. Audit log entry. |
| Install partial (network drop mid-extract) | Roll back. Clean up temp directory. |

#### Testing

- Unit: catalog schema validation, install path resolution, cache TTL.
- Integration: mock GitHub fetch responses.
- Security: tampered checksums rejected, malformed manifests rejected.

### 3.3 Sidecar IPC Pattern (used by Stream B)

#### Generalized abstraction

The existing Parakeet voice-input sidecar is currently a direct implementation. Refactor to a `Sidecar` trait so Piper TTS and future sidecars share lifecycle, IPC, and error handling.

```rust
// src-tauri/src/sidecars/mod.rs
pub trait Sidecar {
    fn name(&self) -> &str;
    fn binary_path(&self) -> PathBuf;
    fn start(&mut self) -> Result<()>;
    fn stop(&mut self) -> Result<()>;
    fn is_running(&self) -> bool;
    fn send_request<R: Serialize, T: DeserializeOwned>(&self, req: R) -> Result<T>;
}

pub struct PiperSidecar { /* ... */ }
pub struct ParakeetSidecar { /* refactored from current direct impl */ }
```

#### Communication protocol

stdio JSON-lines (one request, one response, framed by newline). Tauri command wraps each sidecar. Streaming responses where applicable: Parakeet streams partial transcripts, Piper streams audio chunks for long responses.

#### Lifecycle

- Sidecar spawned lazily on first use.
- Kept alive across requests (cold-start once, warm reuse).
- Stopped on app quit.
- Auto-restart on crash (max 3 retries before surfacing error).

#### Error handling

| Failure | Behavior |
|---|---|
| Binary missing or corrupted | Toast: "TTS not available, re-download in Updater." |
| Sidecar crash | Auto-restart up to 3 times. Surface only on persistent failure. |
| Slow response (over 2 seconds elapsed) | Progress indicator. |

#### Testing

- Rust unit: lifecycle, request serialization.
- Integration: full round-trip request, response deserialized.
- E2E: trigger sidecar action via UI, expected output appears.

### 3.4 i18n Key-Extraction Convention (used by Stream E)

#### Tool stack

- `react-i18next` (runtime, industry standard for React).
- `i18next-parser` (build-time string extraction).
- Locale files: `src/locales/{en,es,de}.json`.

#### Key naming convention

Hierarchical dot notation, lowercase kebab-case leaves: `<page>.<component>.<element>`.

Examples: `chat.input.send-button`, `settings.api-keys.title`, `marketplace.templates.install-cta`, `error.attachment.too-large`.

#### Source of truth

`en.json` is canonical. Spanish and German generated by LLM-translation script (Section 8.4). Light human review pass after generation.

#### Custom ESLint rule

`eslint-plugin-projelli-i18n` detects JSX text content with 3 or more alphabetic words not wrapped in `t()` or `<Trans>`. Warns in dev, errors in CI. Allowed bypasses: code blocks, single-word labels (OK, Yes, No), debug-only strings gated by `import.meta.env.DEV`.

This rule runs in CI for ALL stream PRs from day one. Catches missed strings during streams A/B/C/D rather than at end.

#### Locale detection

First launch: read OS locale via Tauri `os::locale()`, default to closest supported (en/es/de). User overrides in Settings → General → Language. Persist in settingsStore.

#### Pluralization and interpolation

Use i18next's CLDR plural rules. ES and DE handled correctly. No string concatenation in code; always single keys with interpolation tokens like `{{count}}`.

#### Error handling

| Failure | Behavior |
|---|---|
| Missing key in current locale | Fall back to English. Audit log entry. |
| Translation file fails to load | Silent fall-back to English. |

#### Testing

- Unit: key resolution, fallback logic.
- Build-time: i18next-parser warns on missing keys, fails build with `--fail-on-warnings` flag.
- Manual QA: load every page in ES and DE, fix layout issues (German runs roughly 30% longer than English).

#### Cost tracking

- Claude vision: roughly 85 tokens per 512×512 image, scales linearly.
- OpenAI vision: roughly 85 base + 170 per detail tile.
- Gemini vision: roughly 258 tokens per image.
- Each provider's cost-meter integration uses its documented formula.
- Cost-meter UI shows breakdown: "Text: 1.2K tok, Images: 340 tok, Est cost: $0.014".

### 4.3 A3: PDF Chat (Hybrid Path)

#### Routing logic

```typescript
async function preparePdfForProvider(pdfAtt, provider, model) {
  if (provider.name === 'claude' && provider.supportsNativePdf(model)) {
    return { mode: 'native', bytes: await readPdf(pdfAtt) };
  }
  const text = await extractPdfText(pdfAtt);
  return { mode: 'text-extract', text };
}
```

#### PDF.js bundling

- `pdfjs-dist` added as dependency. Lazy-loaded; not in main bundle.
- Web worker required (PDF.js standard pattern). Copy `pdf.worker.min.js` to `public/`.
- `extractPdfText(bytes): Promise<{ pages: string[]; pageCount: number; encrypted: boolean }>`.

#### UI indicator (in chat history)

- Native: green chip "📄 contract.pdf · 12 pages · native PDF". Figures and tables preserved.
- Extracted: yellow chip "📄 deck.pdf · 8 pages · text extracted". Figures and tables omitted.
- Tooltip explains the difference.

#### Pre-send preview (text-extract mode)

Show first 200 characters of extracted text. User verifies content looks correct.

#### Cost preview before send

- Native Claude PDF: roughly 3000 tokens per A4 page.
- Text-extract: token count from extracted text directly.
- Tooltip on send button: "Send (~84K tokens, ~$0.27)".

#### Edge cases

- Encrypted PDF: surface error, don't crash. PDF not attached.
- Scanned/image-only PDF (extraction near-empty): warning chip, offer "send as native PDF anyway" if Claude. OCR support deferred to future.

### 4.4 A4: PDF to RAG Indexing

Extends existing M1 RAG indexer to include PDF text.

#### Implementation

- During workspace re-index, walker finds `.pdf` files.
- For each: run `extractPdfText` (same code path as A3).
- Chunk text per page (or per ~512-token segment).
- Embed via local embeddings model (already in place from M1).
- Store in existing RAG SQLite DB.

#### Opt-in setting

`Settings → Memory / RAG → Include PDFs in workspace index`. Default OFF for v2.0. Tooltip explains tradeoff (CPU and disk cost during indexing).

#### Privacy

All embedding happens locally (Rust-based embedding crate from M1). PDF text never leaves device unless user explicitly attaches the PDF to a chat.

### 4.5 A5: Long-Context UX

#### Cap lift

Settings → AI → Context Token Limit max raised from 200K to 1M. Default stays at 200K (existing users not auto-bumped).

#### Capability detection per provider

- Claude: detect API-key tier. Tier 2+ unlocks 1M for Sonnet.
- Gemini: 1.5 Pro and 2.0 support 1M natively.
- OpenAI: max 200K (o1 models). Flag as "200K cap" on those models in picker.
- Ollama: model-dependent, runtime probe.

Model picker shows context limit inline.

#### Warning UX

- Setting limit over selected model's capability: inline warning, suggest model swap.
- Approaching limit during chat (over 80%): warn before send.

#### Cost preview

Visible at bottom of chat input: "Context: 127K of 200K, ~$0.38 next message at Sonnet". Updates in real time as user types.

#### Summarization compression

- Triggered manually via Compress button OR automatically when send would exceed limit.
- Algorithm:
  1. Keep most recent N turns intact (configurable, default 6).
  2. For older messages, batch into groups of roughly 10K tokens.
  3. Send each group to a fast model (`claude-3-5-haiku` or `gpt-4o-mini`) with prompt: "Summarize this conversation segment, preserving names, decisions, file references, and pending questions."
  4. Replace original messages in the active context with summary, marked with visual indicator: ✂️ "Compressed: 14 messages → 1.2K tokens. [Expand]".
  5. Original messages retained in chat history file (not lost), just not sent to AI on subsequent turns.
  6. Audit log: `context_compressed` event with before/after token counts.

#### Compression edge cases

- Attachments in compressed messages: keep references, drop bytes from context. Saves tokens, preserves audit trail.
- User wants older context: click [Expand] on compressed segment, temporarily un-compresses for next send.

## 5. Stream B: TTS Sidecar

### 5.1 Architecture

When user clicks "Read aloud" on an AI response, text gets piped to local TTS engine (Piper) running as a sidecar binary. Piper produces audio bytes, played back through the browser's Web Audio API. All on the user's machine. No API key, no cloud round-trip, free at the margin, works offline.

### 5.2 Components

- `PiperSidecar` (Rust): implements `Sidecar` trait from §3.3. Manages Piper binary lifecycle.
- `TTSService` (TypeScript): high-level API. `tts.speak(text, voiceId)`, `tts.stop()`, `tts.list()`.
- "Read aloud" button: small icon on each AI message in chat panel. Keyboard shortcut Ctrl/Cmd+Shift+R when message focused.
- Settings → Voice → Output section: enable/disable, voice picker (with click-to-preview), playback speed slider.
- Audio player UI: small inline control bar appears below the message being read (pause / stop / scrub).

### 5.3 Bundled assets

- Piper binary (~1 to 2 MB per platform: Win x64, Mac arm64, Mac x64, Linux x64).
- Bundled English voice (`en_US-amy-medium`). Roughly 30 to 60 MB.
- Spanish voice (`es_ES-mls-medium`) and German voice (`de_DE-thorsten-medium`) lazy-downloaded on first use.
- Voice catalog hosted on Projelli's static CDN (same Caddy + tunnel pattern as marketing site).

### 5.4 Streaming support

Long AI responses (multi-paragraph) take seconds to synthesize. Streaming starts playback at the first chunk while synthesis continues in background. Piper supports streaming output. Implementation: framed audio chunks via Tauri IPC, ring buffer in audio player.

For short responses (under roughly 5 seconds of audio), buffer-then-play is simpler and latency difference does not matter. Heuristic: stream if text length over 500 chars, otherwise buffer-then-play.

### 5.6 Data flow

1. User clicks "Read aloud" on AI message (or hits keyboard shortcut).
2. `TTSService.speak(text, voiceId)` triggers Tauri `invoke('tts_speak', { text, voiceId })`.
3. Rust spawns Piper sidecar if not running (cold start once, warm reuse after).
4. Sidecar reads text via stdin, produces WAV bytes via stdout.
5. Bytes streamed back via Tauri IPC channel.
6. Frontend Web Audio API plays the bytes.
7. Inline player UI shows progress, supports pause/stop/scrub.
8. Audit log: `tts_played` event with text length, voice ID, timestamp.

#### Plugin API surface (v2.0 minimum viable subset)

```typescript
interface PluginAPI {
  readonly pluginId: string;
  readonly version: string;

  commands: {
    register(id: string, handler: () => void | Promise<void>): void;
    invoke(id: string): Promise<void>;
  };

  toolbar: {
    addButton(spec: ToolbarButtonSpec): void;
    removeButton(id: string): void;
  };

  sidebar: {
    addPanel(spec: SidebarPanelSpec): void;
    removePanel(id: string): void;
  };

  editor: {
    getSelection(): Promise<{ text: string; range: Range } | null>;
    getContent(): Promise<string>;
    replaceSelection(text: string): Promise<void>;
    insertAtCursor(text: string): Promise<void>;
  };

  workspace: {
    listFiles(path?: string): Promise<FileNode[]>;
    readFile(path: string): Promise<string>;
    writeFile(path: string, content: string): Promise<void>;  // requires workspace:write
  };

  ai: {
    invoke(opts: { prompt: string; system?: string }): Promise<string>;
    // Uses user's currently configured provider + model.
    // Plugin never sees the user's API key.
  };

  storage: {
    get(key: string): Promise<unknown>;
    set(key: string, value: unknown): Promise<void>;
    remove(key: string): Promise<void>;
  };

  network: {
    fetch(url: string, opts?: RequestInit): Promise<Response>;
  };

  settings: {
    addPage(spec: SettingsPageSpec): void;
    get(key: string): Promise<unknown>;
    set(key: string, value: unknown): Promise<void>;
  };

  notify: {
    info(msg: string): void;
    warn(msg: string): void;
    error(msg: string): void;
  };
}
```

| Permission | Grants | User-prompted? |
|---|---|---|
| `workspace:read` | Read any file in workspace | Yes, on install |
| `workspace:write` | Write/modify files in workspace | Yes, on install |
| `editor:selection` | Read current editor selection | Yes, on install |
| `editor:write` | Insert/replace in editor | Yes, on install |
| `ai:invoke` | Send prompts using user's configured provider | Yes, on install (with cost note) |

### 6.5 C2: Sandboxed Plugin Runner

#### Architecture

```
┌─────────── Main thread (Projelli UI) ───────────┐
│                                                  │
│  PluginManager                                   │
│  ├── Loads enabled plugins on app start          │
│  ├── For each plugin: spawn dedicated worker     │
│  ├── Holds plugin manifests + permissions        │
│  └── Routes API calls between worker + main      │
│                                                  │
│  Permission Enforcer (runs in main thread)       │
│  └── Every API call from worker checks perm      │
│                                                  │
│  API Bridge                                      │
│  └── Serialize args, postMessage, worker         │
└──────────────────────────────────────────────────┘
              ↕ postMessage (structured clone)
┌────── Web Worker (per plugin, isolated) ────────┐
│                                                  │
│  Plugin Runtime                                  │
│  ├── Loads plugin's index.js                     │
│  ├── Provides API proxy to plugin code           │
│  └── Calls plugin.activate(api) on start         │
│                                                  │
│  Plugin Code (3rd-party, untrusted)              │
│  └── Plugin's actual logic runs here             │
└──────────────────────────────────────────────────┘
```

#### Components

- `PluginManager` (main thread): discovers installed plugins, manages lifecycle, holds manifests.
- `PluginWorkerHost` (main thread, one per active plugin): owns the worker, routes messages, terminates on uninstall.
- `PluginPermissions` (main thread): enforces declared permissions on every API call.
- `PluginRuntime` (worker thread): initializes per-plugin, exposes API proxy, runs plugin code.
- `PluginAPIProxy` (worker thread): every API method is wrapped postMessage call.
- `PluginManifestSchema` (shared): Zod or similar; validates manifests on install + load.

#### Data flow (a plugin command invocation)

1. User triggers a command (toolbar button OR command palette OR keyboard shortcut).
2. Main thread looks up command's plugin owner. Routes via `PluginWorkerHost.invokeCommand(id)`.
3. postMessage to worker: `{ type: 'invoke-command', commandId }`.
4. Worker's `PluginRuntime` finds registered command handler, calls it.
5. Plugin code calls `api.editor.getSelection()`. `PluginAPIProxy` postMessages back to main.
6. Main thread's `PluginPermissions` checks plugin has `editor:selection` permission.
7. If yes: main thread reads editor selection, postMessage response back to worker.
8. If no: main thread responds with error, worker promise rejects in plugin code.
9. Plugin completes its logic, returns to runtime.
10. Runtime postMessages "done" back to main.
11. Audit log: `plugin_executed` event with plugin id, command, duration.

#### Sandboxing boundaries

Enforced by web worker:

- No DOM access (worker has no `document`).
- No direct filesystem access (worker has no `fs` or Tauri `invoke`).
- No access to other plugins' state (separate workers, no shared memory).
- No access to user's API keys (AI calls go through main-thread proxy that uses user's keychain).
- Crash isolation: plugin throwing or infinite-looping doesn't affect main thread.

#### Sandboxing limitations (be honest in docs)

- Same-origin cookies and localStorage CAN'T be reached (good).
- BUT: if plugin has `network` permission, it can exfiltrate data the user gave it. Permission consent is the gate, not technical.
- Web Workers run with full JS power within their boundary. High-CPU plugin can slow that worker. Projelli stays responsive.

#### Lifecycle

- Install: manifest validated, files extracted, permissions consent dialog.
- Enable: spawn worker, load plugin, call `activate(api)`.
- Disable: call `deactivate()` (with timeout), terminate worker, unregister UI elements.
- Uninstall: disable + delete plugin folder.
- Crash: terminate worker, surface error, offer "Restart plugin" + "Disable plugin".
- Update: disable old, install new, enable. State in `.projelli/plugins/<id>/data/` preserved across updates.

#### Custom ESLint rule

This rule runs in CI for ALL stream PRs from day one.

### 8.3 E2: String Extraction Sweep

#### Approach

1. Run `i18next-parser` in extract-only mode. Builds initial `en.json`.
2. Use custom ESLint rule with `--fix` to flag every hardcoded string.
3. Sweep agent visits each flagged location, picks key per naming convention, wraps string in `t()`, adds key to `en.json`.
4. Tricky cases (interpolation, plurals, conditional strings) handled manually.

#### Naming convention reminder

`<page>.<component>.<element>` in lowercase kebab-case.

Examples: `chat.input.send-button`, `settings.api-keys.title`, `marketplace.templates.install-cta`, `error.attachment.too-large`.

#### Interpolation example

```typescript
// Before
<p>You have {count} unread messages</p>

// After
<p>{t('chat.notifications.unread', { count })}</p>

// en.json
"chat.notifications.unread": "You have {{count}} unread message",
"chat.notifications.unread_other": "You have {{count}} unread messages"
```

#### Scope

Every component file with JSX text, every label in Settings, every error message, every toast, every empty-state message.

NOT translated:
- Code (variable names, function names, comments).
- Console logs (developer-facing).
- File paths.
- Test fixtures.
- Dev-only messages gated by `import.meta.env.DEV`.

### 8.4 E4: LLM Translation Script

#### Script (`scripts/translate-i18n.mjs`)

```javascript
import Anthropic from '@anthropic-ai/sdk';
import en from '../src/locales/en.json' assert { type: 'json' };
import es from '../src/locales/es.json' assert { type: 'json' };
import de from '../src/locales/de.json' assert { type: 'json' };
import { writeFileSync } from 'fs';

const client = new Anthropic();

async function translate(targetLang, existingTranslations) {
  const missing = Object.entries(en).filter(([k, v]) =>
    !existingTranslations[k] || existingTranslations[k]._sourceHash !== hash(v)
  );

  if (missing.length === 0) {
    console.log(`${targetLang}: nothing to translate`);
    return existingTranslations;
  }

  const batches = chunk(missing, 50);
  const result = { ...existingTranslations };

  for (const batch of batches) {
    const response = await client.messages.create({
      model: 'claude-3-5-sonnet-latest',
      max_tokens: 4000,
      system: `You are translating UI strings for Projelli, a desktop AI workspace app. 
        Target language: ${targetLang === 'es' ? 'Spanish (es-ES)' : 'German (de-DE)'}.
        Rules:
        - Maintain interpolation tokens like {{count}} unchanged
        - Keep punctuation style of the target language
        - Keep tone consistent with a productivity app
        - Short labels (buttons, menu items) should stay concise
        Output strict JSON: { "key": "translation", ... }`,
      messages: [{
        role: 'user',
        content: `Translate these ${batch.length} strings:\n${JSON.stringify(Object.fromEntries(batch), null, 2)}`,
      }],
    });

    const translations = JSON.parse(response.content[0].text);
    for (const [key, value] of Object.entries(translations)) {
      if (existingTranslations[key]?._locked) continue;  // skip human-locked entries
      result[key] = value;
      result[key + '._sourceHash'] = hash(en[key]);
    }
  }

  return result;
}

const newEs = await translate('es', es);
const newDe = await translate('de', de);
writeFileSync('src/locales/es.json', JSON.stringify(newEs, null, 2));
writeFileSync('src/locales/de.json', JSON.stringify(newDe, null, 2));
console.log('Translation complete. Review diffs before committing.');
```

#### Determinism

Same input + same model = essentially same output. Re-runs that produce no diff are no-ops.

#### Re-translation triggers

- Any English string change. Hash changes. Script re-translates that key only.
- New keys: translated on next run.
- Removed keys: cleaned up automatically (i18next-parser does this).

### 8.5 E5: Light Human Review Pass

#### Process

1. After E4 runs, `git diff src/locales/es.json src/locales/de.json` shows changed strings.
2. Reviewer scans diff, focusing on short button/menu labels, strings with interpolation, idiomatic phrases.
3. Flagged strings get manual fix in JSON file directly.
4. Re-run E4 won't re-translate manually-fixed strings (they have `_locked: true` marker).

#### Lock mechanism

```json
{
  "settings.api-keys.title": "Llaves API",
  "settings.api-keys.title._locked": true,
  "settings.api-keys.title._sourceHash": "abc123"
}
```

#### Reviewer recruitment

- Try first: native Spanish/German speakers in existing buyer cohort (free in exchange for marketplace credit).
- Fall back: pay a small Fiverr/Upwork translator for one review pass.
- Documented framing: "Localization quality improves over time. Community review welcomed via PR."

### 8.6 E6: Locale Detection + Language Picker

#### OS locale detection (first launch)

```typescript
// src/lib/locale-detect.ts
import { os } from '@tauri-apps/api';

const SUPPORTED = ['en', 'es', 'de'];

export async function detectLocale(): Promise<string> {
  try {
    const osLocale = await os.locale();
    const lang = osLocale.split('-')[0].toLowerCase();
    return SUPPORTED.includes(lang) ? lang : 'en';
  } catch {
    return 'en';
  }
}
```

#### App launch wiring

```typescript
import i18n from './i18n';
import { detectLocale } from './lib/locale-detect';
import { useSettingsStore } from './stores/settingsStore';

const userLang = useSettingsStore.getState().language;
const lang = userLang ?? await detectLocale();
i18n.changeLanguage(lang);
```

#### Settings UI

```
Language        [English ▾]
                 ├── English
                 ├── Español
                 └── Deutsch
```

Toggling triggers `i18n.changeLanguage()` + persists to settingsStore. No reload required.

#### Web demo specifics

Web demo runs in browser, no Tauri `os::locale()`. Use `navigator.language` instead.

#### Audit log

`language_changed` event records old → new locale.

#### QA checklist (per language)

- Every page in app loads without missing-key errors.

- Every label aligns properly (forms especially).

| Risk | Mitigation |
|---|---|

## 9. Integration & Shipping Plan

### 9.1 Branch / worktree model

Each stream gets its own git worktree (separate working directory tied to a branch on the same repo).

#### Worktree structure

```
~/projelli/                              (main worktree, branch: main)
~/projelli-worktrees/
├── foundations/                         (branch: feature/foundations)
├── stream-a/                            (branch: feature/stream-a-attachments)
├── stream-b/                            (branch: feature/stream-b-tts)
├── stream-c/                            (branch: feature/stream-c-marketplace-plugins)
├── stream-d/                            (branch: feature/stream-d-mobile-web)
└── stream-e/                            (branch: feature/stream-e-i18n)
```

Each worktree shares git history with `~/projelli/` (cheap, no full repo clone). Each runs its own `npm install`.

#### Branching pattern within each stream

- Foundations branch merges to main FIRST (everything else depends on it).
- Each stream sends incremental PRs at subtask boundaries (A1, A2, A3, ...).
- Streams pull from main periodically to stay current.
- Long-running stream branches are anti-pattern. Last alive is Stream C (plugin system has many subtasks).

Why continuous-incremental over long-running: long unmerged branches drift, conflict, rot. Continuous merges surface integration problems while small.

### 9.2 Merge order

| Order | Item | Dependencies |
|---|---|---|
| 0 | Foundations branch (§3 plumbing, ESLint rule, type definitions) | None. Runs first. |
| 1 | Stream B (TTS) | Foundations §3.3 (sidecar pattern). |
| 2 | Stream A (attachments + multimodal + PDF + long context) | Foundations §3.1 (chat-attachment system). |
| 3 | Stream D (web demo first, mobile reader after spike passes) | Foundations §3.4 (i18n keys). `apps/` workspace refactor. |
| 4 | Stream C (templates marketplace, plugin system after spike passes) | Foundations §3.2 (GitHub catalog format). |
| 5 | Stream E (i18n migration sweep + translation + QA) | All other streams merged. |
