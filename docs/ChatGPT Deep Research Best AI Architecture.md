# Best Agent Architecture for Building Your AI CRM

## Bottom line

For a software project like yours, the most robust architecture is **not** a meta-coordinator supervising multiple coordinators that then supervise workers. The research and vendor guidance point the other way: start with the **simplest topology that preserves clear ownership**, which in practice means **one primary lead agent that owns the plan and final synthesis, plus a small set of narrow specialists that behave like tools or short-lived subagents**. Anthropic says the strongest production systems tend to use “simple, composable patterns” rather than elaborate frameworks, and OpenAI similarly recommends maximizing a single agent’s capabilities before splitting into multiple agents because extra agents add complexity and overhead. citeturn6view0turn10view6

That conclusion is especially strong for coding. Anthropic’s own multi-agent research notes that, unlike broad research tasks, **most coding tasks have fewer truly parallelizable branches**, and today’s LLM agents are **not yet especially good at coordinating and delegating to one another in real time**. That is almost a direct description of the issue you are seeing: your coordinators are “decent,” but misunderstandings creep in when they talk to each other or to the meta-coordinator. In other words, the failure mode you described is not incidental; it is a known weakness of current multi-agent coding setups. citeturn12view0

My strongest recommendation is this: **collapse the meta-coordinator layer**, keep **one top-level project lead**, keep nesting shallow, and make workers communicate primarily through **structured artifacts and verification outputs**, not through free-form back-and-forth conversation. OpenAI’s current Codex guidance even defaults `agents.max_depth` to `1` and explicitly warns that deeper recursive delegation increases token use, latency, and unpredictability. citeturn19view0turn19view3

## What current research and platform guidance imply

The closest thing to a consensus across Anthropic, OpenAI, Microsoft, and LangChain is that **multi-agent architecture is valuable when work divides cleanly into independent branches**, but it becomes fragile when coordination itself becomes the main job. Anthropic’s Research system worked well because the lead agent could split a question into parallel, largely independent investigations; in that setting, multi-agent breadth helped a lot. But the same Anthropic write-up cautions that coding is different, because dependencies are tighter and real-time coordination is weaker. citeturn12view0

OpenAI’s orchestration guidance lands in almost the same place. It distinguishes **handoffs** from **agents-as-tools**, and recommends the manager-style pattern when the main agent should remain responsible for the final answer while specialists do bounded pieces of work. It also says to give each specialist a narrow job, keep contracts short and concrete, and split only when the next branch genuinely needs different instructions, tools, or policy. That is a strong argument against your current multi-hop stack, because a meta-coordinator plus two coordinators creates several additional ownership transfers without changing the fundamental contract of the work very much. citeturn10view0turn10view1

Anthropic’s newer Claude Code documentation pushes in the same direction. Subagents are framed as useful when a side task would otherwise flood the main context with logs, search output, or file contents; each subagent gets its own context window and returns a summary. Agent teams, by contrast, are for workers that need to message each other directly, but Anthropic labels them experimental, notes known limitations around session resumption and task coordination, and says they work best when teammates can operate independently. For sequential tasks, same-file edits, or work with many dependencies, Anthropic says a single session or subagents are more effective. citeturn5view2turn24view4turn24view5turn24view6

If you abstract away the product differences, the architecture guidance converges on a simple principle: **use one lead for ownership, use direct worker calls for bounded work, use team-style peer messaging only when collaboration itself is the point, and move from conversational orchestration to scripted orchestration when scale becomes large enough that conversation is the bottleneck**. Anthropic’s dynamic workflows explicitly recommend this jump when a task needs more agents than one conversation can coordinate or when you want the orchestration encoded as a rerunnable script rather than held in model context. citeturn23view1turn25view0

## Assessment of your past and current setups

Your earlier setup, where **Fable 5 acted as a coordinator managing its own Opus 4.8 subagents in separate tmux sessions**, was directionally stronger than your newest stack because it kept a single top-level owner while still exploiting parallelism. Public Anthropic guidance currently positions **Claude Opus 4.8** as the starting point for complex agentic coding and **Claude Fable 5** as the highest-capability option when you need the strongest available model. That means your instinct to place the most capable model at the coordination layer was reasonable. citeturn4view11turn3search8

Where the architecture started to drift is when you introduced a **meta-coordinator supervising two coordinators**. That adds another translation layer, another summarization layer, another place where task boundaries can blur, and another place where context can be compressed incorrectly. OpenAI’s current Codex docs explicitly discourage recursive delegation as a default by keeping subagent depth at `1` unless you specifically need deeper nesting, because repeated fan-out makes systems more expensive and less predictable. Anthropic’s guidance likewise emphasizes clear delegation messages with explicit objectives, output formats, source/tool guidance, and task boundaries, precisely because vague or multi-hop delegation causes duplicated work and misinterpretation. citeturn19view1turn12view1

So, I would rate your progression this way. The first serious coordinator-worker design was **structurally sound but under-specified**. The current meta-coordinator design is **over-layered**. It is solving the wrong problem: you are adding hierarchy to compensate for planning difficulty, when what the system actually needs is **better contracts, better artifact flow, and shallower authority lines**. That is consistent with Anthropic’s warning that the successful systems are usually simpler than people expect, and with OpenAI’s warning that splitting too early creates more prompts, more traces, and more approval surfaces without necessarily improving the workflow. citeturn6view0turn10view1

Your newest model allocation also looks partly right and partly misplaced. On the OpenAI side, the current docs do **not** appear to expose a product officially named “Codex 5.6”; instead, OpenAI’s current official naming distinguishes the **GPT-5.6 family**—including **Sol, Terra, and Luna**—and a separate **GPT-5-Codex** entry optimized for agentic coding. Within those docs, **GPT-5.6-Terra** is described as a speed-and-efficiency choice that works well for exploration, read-heavy scanning, document processing, and parallel workers that return distilled results, while **GPT-5.6** is the recommended starting point for demanding, ambiguous, multi-step agent work. In practical terms, Terra-high can be excellent for explorers and auditors, but it is not the best default for every worker if those workers are doing the hardest implementation logic. citeturn4view9turn4view10turn19view4turn18view0

## The structure I would recommend instead

The best-fit topology for your stage looks like this:

```text
You
└── Lead architect-executor
    ├── Explorer
    ├── Implementer A
    ├── Implementer B
    ├── Reviewer / verifier
    └── Docs / API / compliance researcher
```

The key difference from your current setup is that **there is only one true owner of the work**. That lead agent creates the plan, chooses workers, receives their outputs, decides what to trust, and decides when the task is done. Workers do not negotiate freely with each other by default. If they need shared state, they read and write to artifacts such as `PLAN.md`, `TASKS.md`, spec files, or test outputs. This mirrors OpenAI’s “agents as tools” guidance, where the main agent stays responsible for the final answer and specialists stay bounded, and it aligns with Anthropic’s advice to keep delegation precise and context separated. citeturn10view1turn12view1turn15view1

In your case, I would use **one strong lead** and **two to four direct workers**, not a tree of coordinators. Two workers is often enough for a feature branch that divides into build-and-verify or frontend-and-backend. Three or four works when the work genuinely splits into implementation, exploration, review, and documentation or compliance support. Anthropic’s own research system sped up materially when it used a small parallel fan-out rather than serial exploration, but Anthropic also says coding has fewer parallel branches than research, which is why I would keep the direct worker count conservative. citeturn12view0turn12view1

For model allocation, I would separate jobs by **cognitive mode**, not just by rank in the hierarchy. A good default mapping is:

- **Lead architect-executor:** use your strongest planning model. In the Anthropic stack, that can mean **Fable 5** when you want the highest-capability top brain, or **Opus 4.8** when you want a model explicitly positioned for complex agentic coding. In the OpenAI stack, the closest equivalent is **GPT-5.6 / Sol-class reasoning** for ambiguous multi-step work. citeturn4view11turn18view0
- **Explorers and read-heavy researchers:** **GPT-5.6-Terra** or Claude subagents on a cheaper/faster tier are appropriate, because OpenAI explicitly positions Terra for exploration, read-heavy scans, large-file review, and parallel workers that return distilled outputs. citeturn19view4
- **Implementers:** use a stronger coding-capable model than Terra when the edit is architecturally meaningful, touches multiple files, or needs iterative debugging. Anthropic recommends Opus 4.8 for complex agentic coding, and OpenAI recommends `gpt-5.6` for demanding agents. citeturn4view11turn19view4
- **Reviewers / security / edge-case checkers:** use **high** reasoning effort, because OpenAI explicitly says `high` is useful when an agent must trace complex logic, check assumptions, or work through edge cases, especially for reviewer-like roles. citeturn19view5

The most important structural rule is this: **do not stack planner on planner on planner**. If you need more scale than one lead plus a few direct workers can handle, the next step should usually be **scripted orchestration**, not another human-language coordinator layer. Anthropic’s dynamic workflows are built for exactly that jump: once work outgrows a handful of subagents or needs systematic cross-checking, the script should hold the loop and intermediate state rather than the lead model’s context window. citeturn23view1turn25view0

## How your agents should communicate

The biggest change I would make is not merely who reports to whom, but **how information crosses the boundary**. Anthropic’s research team found that orchestration quality improved when the lead gave each subagent an explicit objective, output format, guidance on tools and sources, and clear task boundaries. OpenAI’s GPT-5.6 guidance similarly recommends outcome-first prompts with clear constraints and stopping conditions, while its Codex best-practices guide says prompts should specify the goal, context, constraints, and “done when.” Put together, those sources point toward a communication protocol that looks much more like a ticketing system than a conversation. citeturn12view1turn18view2turn8view2

In practice, every delegated task should be a **task card** with a fixed schema. I would require the lead to send workers a written artifact containing: the objective; exact files, modules, or components in scope; relevant context links or files; constraints; required output format; required verification; and explicit out-of-scope boundaries. Workers should return a structured result with: decision or implementation summary; changed files; tests run; evidence; risks; blockers; and recommended next step. That is partly an inference from the sources, but it is a very strong one: the more explicit the contract, the less room there is for coordinator-to-coordinator drift. citeturn12view1turn10view0turn18view2

I would also make **artifact flow** the default channel and **agent chat** the exception. Use `PLAN.md`, `TASKS.md`, an ADR or RFC folder, test reports, screenshot diffs, lint output, and a small machine-readable status file as the system of record. Anthropic’s Managed Agents write-up is especially relevant here: it argues that the durable session should live outside the model’s context window, because long-horizon work eventually exceeds the context window and compaction forces irreversible choices about what to keep. Microsoft’s Magentic-One uses the same basic idea in a different form through a Task Ledger and Progress Ledger. Your system should do the same in repo-local artifacts or an external task store. citeturn21view0turn11view0turn11view1

This is also where your tmux-based setup can improve a lot. Tmux is fine as a process container, but it should not be the coordination layer. The coordination layer should be **artifact-driven state** plus **clear ownership**. Tmux panes or sessions are just execution surfaces. Anthropic’s agent-team docs even note that teammates do not inherit the lead’s conversation history, so task-specific details must be included in the spawn prompt. That is further evidence that relying on conversational context transfer between sessions is brittle compared with explicit artifacts. citeturn24view3

## Verification, isolation, and state management

The most reliable long-running coding agents are built around **verification loops**, not around eloquent planning. Anthropic’s Claude Code best-practices guide says the difference between a session you must watch and one you can walk away from is giving the agent a check it can run: tests, a build, a screenshot comparison, or another pass/fail signal. OpenAI’s Codex guidance says essentially the same thing: ask Codex not only to write code, but to create tests when needed, run checks, confirm the result, and review the diff before you accept it. citeturn13view0turn8view2

So your lead agent should never mark a task complete based only on worker prose. Completion should require at least one of three gates. The first is a **deterministic gate**, such as tests, build, lint, or type checking. The second is an **independent reviewer in a fresh context**, which Anthropic recommends explicitly because the reviewer is less biased toward code it just wrote. The third is a **goal or stop hook** that blocks the run from finishing until completion criteria actually hold. Claude Code’s hooks support both prompt-based and agent-based stop checks, and Anthropic recommends subagent-based verification when file inspection or command execution is needed. citeturn14view1turn15view4turn5view6

Isolation also matters. For parallel sessions that edit code, use **worktrees**. Anthropic’s docs repeatedly recommend worktrees so simultaneous edits do not collide, and both Anthropic and OpenAI warn against running live concurrent tasks on the same files without them. Anthropic also says that if workers touch the same files, you should partition ownership carefully because file conflicts waste effort fast. In your case, the cleanest rule is one worker per owned file surface or per bounded deliverable, not one worker per abstract “thought stream.” citeturn5view7turn25view0turn8view1turn24view2

Finally, manage state outside the live context window. Anthropic warns that long sessions degrade as context fills, and recommends aggressive context management, subagents for investigations, and compaction. Anthropic’s Managed Agents architecture goes further and treats the session log as a durable object outside the context window. For your workflow, that argues for maintaining a compact but explicit persistent layer: `PLAN.md`, `DECISIONS.md`, `TASKS.md`, `OPEN_QUESTIONS.md`, and one status JSON per worker or per run. Use the live conversation for local reasoning; use artifacts for durable control state. citeturn13view0turn15view0turn21view0

## When to use a different pattern

There are times when something more complex than a single lead plus direct workers is warranted. If the work becomes a **large repeated batch**—for example, a repo-wide migration, a security sweep across hundreds of files, or a repetitive audit where each row is independent—then move up from conversational coordination to **workflow orchestration**. Anthropic’s dynamic workflows are designed for cases where work needs more agents than one conversation can coordinate, while Codex’s current subagent tooling also supports structured batch patterns such as CSV-driven jobs. That is the right escalation path for “too much breadth,” not a meta-coordinator. citeturn23view1turn17view0

If you are doing **design exploration** rather than implementation—for example, “compare three architecture options for meeting recordings and transcript indexing,” or “debug this failure by testing competing hypotheses”—then an **agent team** can be useful, because Anthropic says teams are strongest when parallel exploration adds real value and when findings need to be shared and challenged. But even there, the docs say teams add coordination overhead, cost more, are experimental, and are less suitable for sequential or dependency-heavy work. My practical interpretation is: use teams for architecture spikes, pre-coding investigation, and review; use subagents or direct workers for implementation. citeturn24view5turn24view1

One more nuance matters for your stack. Because you are already mixing Anthropic and OpenAI models, I would avoid **cross-vendor chains of command** where one vendor’s model acts mainly as a translator for another vendor’s model. Official guidance from both companies emphasizes their own prompt contracts, tool-routing assumptions, and configuration surfaces. GPT-5.6, for example, explicitly rewards leaner prompts and outcome-first contracts; Anthropic’s research emphasizes detailed delegation messages with boundaries and output formats. My inference is that once you insert multiple coordinators from different model families into the same chain, you amplify “prompt-contract drift” rather than capability. The safest place to mix vendors is at the **worker role level**, not by stacking them into multiple layers of management. citeturn18view2turn12view1

## The specific structure I would use for your project

If I were configuring your coding agents for this AI CRM demo right now, I would use the following operating model.

The **root session** would be a single lead with ownership of the roadmap slice currently being worked. That lead would read `PLAN.md`, update it, choose workers, and synthesize outcomes. I would keep this session on your strongest model tier, because it needs to plan, arbitrate, and decide when a task is done. Anthropic currently recommends Opus 4.8 as the starting point for complex agentic coding and Fable 5 for the highest capability; OpenAI recommends GPT-5.6 for demanding agent work. citeturn4view11turn18view0

Under that lead, I would define **four reusable worker types** and stop there unless a batch workflow truly demanded more scale. The first is an **explorer**, which is read-only and optimized for speed and evidence gathering. The second is an **implementer**, which can edit and run tests within a worktree. The third is a **reviewer**, read-only, with higher reasoning effort and a mandate to reject weak changes. The fourth is a **docs/compliance/API researcher**, which is read-heavy and ideally connected to the right MCP tools or internal docs. This is exactly the kind of narrow, opinionated agent design that current Codex docs recommend. citeturn19view2turn10view0

I would then enforce three rules. First, **only the lead can decide the next branch of work**. Workers do not spawn other workers except in special scripted workflows. Second, **workers do not talk to each other by default**; they write artifacts and return structured summaries. Third, **completion requires evidence**: tests, builds, screenshots, or fresh-context review. Those rules are the cleanest way to resolve the misunderstandings you have been seeing between coordinators and the meta-coordinator. They are also the best match to the current documented strengths and weaknesses of the tooling you are using. citeturn10view1turn14view1turn15view4turn19view1

If you want a concise verdict on your current stack, it is this: **your instincts about strong coordinators and isolated workers were right; your move to a meta-coordinator was the wrong kind of abstraction**. Replace hierarchy with contracts. Replace coordinator-to-coordinator chat with artifacts. Keep one owner. Use cheap fast workers for exploration, stronger workers for implementation and review, and jump to scripted workflows only when the size of the job, not the ambiguity of the plan, is the thing that needs to scale. citeturn6view0turn12view0turn19view4turn23view1
